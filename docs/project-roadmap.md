# SI 템플릿과 포트폴리오 완성 방향

## 만들려는 결과

Vite + React + TypeScript + Ant Design으로 **백엔드 없이 실행 가능한 업무용 프런트엔드 템플릿**을 만든다. JSP·백엔드 경험을 바탕으로 React의 화면·상태·비동기 처리를 익히고, 설계 이유와 검증 결과를 설명할 수 있는 이력서 포트폴리오로 완성한다.

여러 SI 프로젝트에서 반복되는 화면 틀, 화면 이동, 검색·목록·입력, 조회·저장 경계를 제공하는 것이 목표다. 모든 업종의 기능을 갖추거나, 실제 인증·운영 환경까지 준비된 제품이라고 주장하지 않는다. **대표 업무 하나의 완결성과 두 번째 업무를 추가한 증거**로 재사용성을 확인한다.

이 문서는 전체 방향과 완료 기준이다. 작업 순서는 [학습 계획](./learning-plan.md), 1차 동작·데이터 규칙은 [프로토타입 설계](./prototype-design.md)를 기준으로 한다. 현재 구현은 실제 코드로 확인하고 진행 상황과 검증 결과는 작업 종료 시 채팅으로 안내한다. 아래 내용은 지금 한꺼번에 구현할 목록이 아니다.

## 세 번의 완성 지점

그리드는 **AG Grid Community**를 기본으로 사용한다. Ant Design은 레이아웃·입력·버튼·모달 등의 기본 UI를 맡는다. 향후에도 Enterprise 등 유료 버전으로 전환하지 않고 유료 패키지·라이선스·평가판을 도입하지 않는다. Community에 없는 기능은 실제 요구가 생긴 단계에서 직접 개발하며, 미래 확장을 미리 구현하지 않는다.

| 지점 | 결과물 | 완료를 판단할 증거 |
| --- | --- | --- |
| 1차: 업무 흐름 완성 | 공통 Top / Left / Content와 사용자 검색·페이지 이동·등록·수정·삭제 | 정상·빈 결과·대기·실패·재시도, 입력 검증, 페이지 보정을 실제 실행으로 확인 |
| 2차: 재사용 검증 | 공통 코드 조회라는 두 번째 업무 화면, 기존 데이터의 간단한 대시보드, 핵심 자동 검증 | 레이아웃 수정 없이 업무 추가, 업무별 데이터 분리, 새 업무 추가·예제 제거 방법 설명 |
| 3차: 포트폴리오 공개 | 공개 데모, 실행 가능한 저장소, 대표 화면과 짧은 시연 안내, 설계·검증 근거 | 다른 환경에서 설치·실행 가능, 배포 URL 직접 진입·새로고침 확인, 실제 동작과 README 일치 |

백엔드 구현은 위 세 지점의 선행 조건이 아니다. 실제 API 연결은 그 이후의 별도 확장으로 진행한다. 각 지점의 완료 여부는 채팅으로 안내하며, 동작 미확인을 완료로 바꾸지 않는다.

## 1차: 사용자 관리 한 흐름을 끝까지

사용자 관리는 기술 설명용 임시 예제 대신 검색·목록·입력·검증·저장이라는 SI 공통 흐름을 보여 주는 대표 업무로 사용한다.

- 현재까지 만든 공통 틀과 화면 이동을 유지한다.
- 검색 입력, 검색 적용, 페이지 이동, 비동기 조회를 작은 단계로 연결한다.
- 등록·수정·삭제는 정상 저장뿐 아니라 실패·중복 제출·목록 재조회까지 완성한다.
- 모의 데이터는 앱 실행 중 유지되고 새로고침하면 초기화된다. 이 제한을 화면과 README에 안내한다.
- 홈은 프로젝트 안내, 대시보드는 이 시점까지 안내 화면으로 둔다. 완성된 통계 기능으로 표현하지 않는다.

필터·페이지 계산은 먼저 화면에서 익힌 뒤, 비동기 조회 전에 기능 전용 조회 함수 안으로 옮긴다. 화면은 `조건과 페이지 → 목록과 전체 건수`라는 계약을 사용한다. 이 한 번의 이동은 역할 분리를 배우면서 향후 서버 연결 시 재작업을 줄이기 위한 의도적인 단계다.

## 2차: 재사용을 실제로 확인

### 중요한 동작의 자동 검증

사용자 관리가 동작한 뒤, 다른 업무를 추가하기 전에 회귀 검증을 마련한다. 회귀 검증은 새 변경이 기존 동작을 깨뜨렸는지 확인하는 것이다.

- 조회 계약: 검색 조건 조합, 전체 건수, 페이지 경계, 빈 결과.
- 저장 계약: 중복 이메일, 수정 시 자기 이메일 유지, 반환 객체 수정으로 원본이 바뀌지 않음.
- 브라우저 흐름: 검색 후 등록·수정·삭제, 중복 제출 방지, 저장 성공 후 조회 실패 시 조회만 재시도.

먼저 함수 수준 테스트를 하나씩 도입하고, 이후 핵심 브라우저 시나리오를 자동화한다. 도구는 그 단계에서 현재 구성과 공식 문서를 확인해 선정한다. 단순 JSX 스냅샷이나 높은 커버리지 숫자보다 실제 버그를 잡는 검증을 우선한다. 이 도구들은 현재 문서 정비 단계에 설치하지 않는다.

### 두 번째 업무: 공통 코드 조회

기본 대상으로 공통 코드 조회를 선택한다. 코드 그룹 목록을 검색하고 하나를 선택하면 그 그룹의 코드·코드명·사용 여부를 볼 수 있는 작은 화면이다. 전체 CRUD를 다시 만들거나 사용자 관리에 억지로 연결하지 않는다.

작업은 그룹 목록 표시 → 그룹 검색 → 그룹 선택과 상세 코드 조회로 나눈다. 라우트·메뉴·공통 제목·비동기 피드백을 기존 틀에 적용하되, 업무 타입과 규칙은 해당 기능 안에 둔다. 상세 데이터 로딩·빈 값·실패도 해당 동작과 함께 확인한다.

이 과정에서 실제 반복이 확인된 표현만 공통화한다. 모든 화면을 하나의 범용 Table/Form으로 만들거나 옵션이 많은 CRUD 생성기를 만들지 않는다. 목록과 상세 선택의 관계처럼 다른 업무 동작도 수용할 수 있는지가 검증 기준이다.

### 안내 화면을 의미 있는 현황 화면으로

대시보드에는 사용자 전체·활성·비활성 수와 사용자 관리로 가는 링크만 추가한다. 조회한 한 페이지의 행 수를 전체 통계로 쓰지 않고, 같은 모의 저장소를 읽는 요약 조회 함수를 사용한다. 사용자 변경 후 대시보드에 다시 들어오면 수치가 갱신되는지 확인한다. 차트 라이브러리나 실시간 전역 동기화는 필요해질 때 판단한다.

### 템플릿 적용 안내

새 업무를 넣을 때 수정할 라우트·메뉴·기능 폴더와 재사용할 레이아웃·표현을 실제 파일 기준으로 기록한다. 사용자·공통 코드 예제를 제거하거나 교체할 위치도 설명한다. 실제 두 번째 업무 추가 결과로 안내의 정확성을 확인한다.

## 3차: 다른 사람이 실행하고 평가할 수 있게

| 산출물 | 담을 내용 | 확인 방법 |
| --- | --- | --- |
| README | 목적, 현재 기능, 준비 환경·명령, 데모 링크, 데이터 초기화·미구현 범위 | 새 환경에서 문서대로 설치하고 실행 |
| 대표 화면·시연 안내 | 목록 검색, 입력 검증, 저장, 실패·재시도, 두 번째 업무 | 짧은 순서대로 따라 하면 같은 결과 재현 |
| 설계 설명 | 상태 소유자, 업무/공통 경계, mock/API 계약, 도구 도입·보류 이유 | 실제 파일과 사용자 동작을 연결해 설명 |
| 검증 안내 | lint·타입·빌드·자동 테스트·브라우저 결과와 알려진 문제 | 확인 환경·명령·결과를 채팅으로 안내 |
| 배포 데모 | 백엔드·계정 없이 주요 동작 실행, 가상 데이터만 사용 | 홈과 업무 URL 직접 진입, 새로고침, 없는 주소, 키보드 조작 확인 |
| 이력서 설명 | 해결한 문제, 본인이 이해한 설계 선택, 검증·개선 근거 | 미구현 기능·실서버 연동·측정하지 않은 성능을 성과로 쓰지 않음 |

공개 전에 화면 제목·간격·한국어 표현·좁은 데스크톱 화면·키보드 초점·오류 복구를 정리한다. 장식보다 읽기 쉽고 일관된 업무 화면을 우선한다. 기존 번들 크기 경고도 실제 빌드 크기와 초기 로딩을 확인한 뒤 필요하면 화면별 지연 로딩 등을 작은 작업으로 검토한다. 경고 임계값만 올려 해결한 것으로 처리하지 않는다.

배포 서비스는 해당 단계에서 선택한다. `vite preview`는 로컬 빌드 결과 확인용이므로 운영 서버로 사용하지 않는다. 실제 호스팅의 하위 경로와 SPA 주소 처리를 별도로 확인한다. [Vite 배포 안내](https://vite.dev/guide/static-deploy.html)

자동 테스트가 생긴 뒤 CI(저장소의 변경에 맞춰 검사를 자동 실행하는 환경)를 작은 별도 단계로 추가한다. Git 스테이징·커밋·저장소 게시 작업은 기존 지침대로 사용자가 VS Code에서 수행한다.

## 백엔드를 나중에 붙이는 기준

1. 페이지와 컴포넌트는 가상 배열 대신 기능별 조회·저장 함수를 호출한다.
2. 조회에는 검색 조건·페이지를 보내고, 결과는 해당 페이지 목록과 검색된 전체 건수로 받는다.
3. 실제 HTTP 호출은 **Axios**를 사용한다. API 함수 내부에서 요청을 보내고 응답 본문과 데이터 전달 형식(DTO), 페이지 시작 번호, 오류 코드 등을 화면용 계약으로 변환한다.
4. Axios 설치·목록 조회 하나부터 연결하고, 필요한 기본 주소·타임아웃·취소·오류 처리를 작은 작업으로 추가한다. 인증 방식, CORS, 서버 검증은 실제 서버 요구가 정해진 단계에서 구현하고 검증한다.

1차의 메모리 기반 모의 API는 HTTP 요청을 보내지 않으므로 Axios를 설치하지 않는다. HTTP 연결 단계에서도 화면이 Axios 응답 객체에 직접 의존하지 않게 한다. 통신 도구는 Axios로 정하고, 공통 설정과 인터셉터의 범위는 실제 필요에 맞춰 정한다. [Axios 공식 문서](https://axios-http.com/docs/intro)

이는 UI와 데이터 구현의 결합을 줄이는 준비이지, 서버 연결이 파일 하나 교체로 끝난다는 보장은 아니다. 프런트의 입력 검증이나 메뉴 숨김은 서버 검증·권한 검사를 대신하지 않는다. 실제 인증 전까지 모의 로그인 화면을 보안 기능으로 소개하지 않는다.

환경변수가 필요해지면 공개 가능한 API 주소 등에 사용한다. Vite의 `VITE_*` 값은 클라이언트 번들에 포함되므로 비밀키를 넣지 않는다. [Vite 환경변수 안내](https://vite.dev/guide/env-and-mode.html)

## 필요가 생겼을 때만 넓힐 범위

| 후보 | 도입을 판단할 시점 |
| --- | --- |
| 서버 데이터 캐시 도구 | 여러 화면에서 재조회·캐시·무효화 처리가 반복될 때 |
| 전역 상태 도구 | URL·Form·공통 부모로 관리하기 어려운 실제 공유 상태가 있을 때 |
| Axios 공통 처리 확장 | HTTP 연결에 필요한 기본 설정부터 시작하고, 여러 API에서 오류·인증·취소 처리가 반복되면 공통화 |
| HTTP 모킹 도구 | 실제 요청 경로까지 검증하거나 mock과 실서버 전환을 유지할 필요가 생길 때 |
| 로그인·권한 | 인증 주체, 세션·토큰, 서버 권한 계약이 정해졌을 때 |
| 엑셀·파일·다중 탭·대규모 표·모바일 전용 화면 | 적용할 프로젝트나 사용자 동작이 요구할 때 |

현재 필요한 작은 구현을 먼저 완성하고, 반복과 문제를 근거로 확장한다. 학습 능숙도는 기술 이름의 개수보다 사용자 동작부터 화면 변화까지 설명하고 오류를 해결할 수 있는지로 확인한다.
