# 단계별 개발·학습 계획

## 문서의 역할

[전체 로드맵](./project-roadmap.md)의 첫 완성 지점을 [1차 설계](./prototype-design.md)에 맞춰 작은 작업으로 나눈 계획이다. 사용자 요청 한 번에 **작은 작업 하나만** 진행한다. 같은 번호에 A·B가 있으면 각각 별도 작업·이해·검증·커밋 단위다.

이 문서는 단계별 개발 내용·학습 개념·완료 기준·검증 시나리오를 담는다. 현재 진행 위치, 완료 체크, 검증 결과, 작업 이력은 기록하지 않는다. 지침은 AGENTS.md, 전체 방향과 완료 기준은 로드맵, 목표 동작은 설계, 실행 방법과 사용자 안내는 README를 참조한다. 문서는 해당 지침·범위·설계·계획 자체가 바뀌거나 사용자가 문서 수정을 요청할 때만 필요한 부분을 수정한다.

## 한 작업의 진행 방식

1. 현재 코드와 이전 채팅의 완료·미확인 안내를 대조하고 이번에 바뀔 사용자 동작 하나를 짧게 설명한다. 이전 안내가 없으면 코드로 확인할 수 있는 범위와 검증이 필요한 부분을 구분한다.
2. AI가 필요한 파일 수정·개발 명령을 실행한다. 처음 쓰는 명령·옵션과 필요한 새 문법은 이유와 함께 설명한다.
3. 사용자 동작 → 이벤트 → 상태·데이터 → 화면 변화를 실제 변경 코드로 연결한다.
4. 변경에 맞는 코드 검사와 실제 실행을 구분해 확인하고 결과·남은 문제를 채팅으로 안내한다.
5. 완료한 작은 작업과 다음 작은 작업을 계획 문서의 실제 파일명·행 번호·단계명으로 채팅에 안내한다. 계획 문서의 완료 표시를 갱신하지 않는다.
6. 사용자는 코드를 이해하고 질문한다. 확인 질문의 답변 제출을 강제하지 않는다.
7. 실제 누적 변경에 맞는 한글 커밋 메시지를 제안한다. 사용자는 VS Code에서 변경 목록과 최신 수정의 스테이징 여부를 확인하고 직접 커밋한다.

다음 작업은 사용자가 명시적으로 요청할 때 시작한다. 설명할 내용이 너무 많으면 기능 단위를 다시 나누되, 잘못된 성공 안내·처리되지 않은 오류를 남기고 완료라고 하지 않는다.

**채팅 안내 형식:** 'docs/learning-plan.md의 N행 ○○ 단계가 완료되었습니다. 다음은 M행 △△ 단계입니다.' N·M은 안내 시점의 실제 행 번호로 확인한다. 일부만 진행했다면 완료한 범위와 남은 작은 작업을 구분한다. 코드 검사·브라우저 확인 결과와 미확인 사항도 채팅으로 안내하며, 필요한 동작을 확인하지 못했다면 전체 완료로 표현하지 않는다.

## 01–05: 화면 틀과 이동

### 01. Top / Left / Content 배치

- **개발:** 현재 `App.tsx`에 Ant Design `Layout`을 조합한다. Top에 프로젝트 이름, Left에 영역 표시, Content에 기존 검색 화면을 배치한다. 최소 CSS만 추가하며 메뉴 동작은 아직 구현하지 않는다.
- **학습:** JSX 중첩, 컴포넌트 조합, 라이브러리 컴포넌트의 props. 추가한 CSS 속성과 값은 실제 배치 결과로 설명한다.
- **완료 기준:** Top이 전체 너비이고, 아래에 Left와 Content가 좌우로 보인다. 기존 입력·초기화가 계속 동작한다.
- **확인 질문:** 안쪽 `Layout`이 필요한 이유와 기존 검색 화면을 넣은 위치를 설명할 수 있는가?

### 02. 레이아웃 컴포넌트 분리

- **개발:** `AppLayout`, `TopBar`, `SideMenu`로 공통 틀을 분리한다. `AppLayout`은 `children`으로 Content에 표시할 내용을 받는다.
- **학습:** import/export, props 타입, `children`, `ReactNode`, `import type`. `.ts`와 `.tsx`의 용도도 필요한 만큼 짚는다.
- **완료 기준:** 파일을 나눠도 화면과 검색 동작이 동일하며, `AppLayout`에 사용자 검색 로직이 들어가지 않는다.
- **확인 질문:** 다른 업무 화면을 Content에 넣으려면 어떤 부분을 바꾸면 되는가?

### 03. Left 접기·펼치기

- **개발:** `AppLayout`에 접기 상태를 두고 Top 버튼으로 Left 너비를 바꾼다. 버튼과 Left에 필요한 props를 전달한다.
- **학습:** boolean state, 상태를 함께 쓰는 컴포넌트의 공통 부모, 함수 props, 이전 상태를 사용하는 갱신.
- **완료 기준:** 버튼을 반복해 눌러도 Left와 Content 너비가 맞게 바뀌며, 버튼의 조작 의미가 표시된다.
- **확인 질문:** Top과 Left가 각각 접기 state를 가지면 어떤 문제가 생길 수 있는가?

### 04. URL로 홈·대시보드·사용자 화면 이동

- **개발:** React Router를 설치한다. 작은 `HomePage`, `DashboardPage`와 사용자 화면의 시작점인 `UserPage`를 만든다. 현재 코드에는 검색 화면이 없으므로 사용자 화면은 제목과 안내부터 표시한다. 공통 틀 아래에 `/`, `/dashboard`, `/users`를 연결하고 Left에서 이동한다.
- **학습:** URL과 화면의 관계, `BrowserRouter`, `Routes`, `Route`, `Outlet`, `Link`. 일반 새로고침 이동과 앱 내부 화면 이동의 차이.
- **완료 기준:** 메뉴를 누르면 URL과 Content가 함께 바뀌고 공통 틀은 유지된다. 주소 직접 입력과 브라우저 뒤로 가기가 동작한다.
- **확인 질문:** 메뉴를 클릭할 때 Content를 바꾸는 기준은 어떤 값인가?

### 05. 현재 메뉴와 없는 주소 안내

- **개발:** `useLocation`으로 메뉴 선택을 URL에 맞춘다. 없는 주소는 공통 틀 밖의 `NotFoundPage`에서 전체 화면으로 안내하고 홈 링크를 제공한다.
- **학습:** 조건에 따른 값 계산, 별도 state 없이 현재 값에서 표시를 결정하는 방식, `*` 경로.
- **완료 기준:** 뒤로·앞으로 가기에도 메뉴 선택이 맞는다. 없는 주소에서는 오류 안내가 보이고 홈으로 돌아갈 수 있다.
- **확인 질문:** 선택 메뉴를 state로 따로 저장하지 않는 이유는 무엇인가?

## 06: 사용자 타입과 정적 표

### 06. 사용자 타입과 목록 표

- **개발:** `YN`, `User`, 가상 사용자 25건 이상을 정의하고 AG Grid Community에 표시한다. 우선 페이지 나누기 없이 표를 확인한다. 앱의 `strict` 검사를 켜고 발생한 타입 오류를 함께 해결한다. 검색 Form과 필터는 08에서 추가한다.
- **학습:** 객체·배열 타입, 문자열 리터럴 유니온, 타입 추론, `strict`, `ColDef<User>`·`AgGridReact<User>`의 제네릭 사용, `getRowId`. 타입 검사가 실행 중 데이터 검증을 대신하지 않는다는 점.
- **완료 기준:** 필드에 맞는 열과 Y·N 표시가 보이고, ID로 행을 식별한다. 엄격한 타입 검사에서도 빌드가 통과한다.
- **확인 질문:** `activeYn: string` 대신 두 값만 허용하면 어떤 잘못을 미리 찾을 수 있는가?

## 06-V: 다음 구현 전 현재 화면 실행 확인

- **작업:** 현재 앱을 브라우저에서 실행하고 아래 확인표의 '기존 기능'과 '06-V 전용'을 검증한다. 제거된 검색 입력이나 과거 Left 너비는 재현하지 않는다.
- **확인:** 1280×720과 1024×768의 배치·스크롤, 메뉴 접기·복원, 세 화면 이동, 시스템명 홈 이동, 뒤로·앞으로, 직접 주소·없는 주소, 사용자 25행과 Y/N·빈 부서 표시.
- **완료 기준:** 실행 환경과 결과를 채팅으로 안내한다. 문제를 찾으면 해당 문제의 작은 수정부터 수행한다. 브라우저에 접근하지 못했다면 미확인을 유지하고 실제 확인 항목을 사용자에게 안내한다.
- **의미:** 코드 검사와 실제 동작 확인을 구분한다. 이 작업에서 07 구현까지 시작하지 않는다.

## 07–09: 목록과 검색

### 07. 사용자 표의 역할 분리

- **개발:** AG Grid Community 표 표시를 UserTable로 옮기고 User[]를 props로 받는다. 기존 테마 연결을 유지하며 수정·삭제용 props는 아직 추가하지 않는다.
- **학습:** 배열 props의 타입, 부모에서 자식으로 데이터 전달, 컴포넌트를 나누는 기준.
- **완료 기준:** 표가 가상 데이터를 직접 가져오거나 변경하지 않고 같은 25건·열·스크롤을 표시한다.
- **확인 질문:** 페이지의 목록이 바뀌면 표는 어떤 경로로 새 값을 받는가?

### 08-A. 이름 검색과 제출

- **개발:** 현재 없는 검색 입력을 UserSearchForm으로 새로 추가한다. 이름 입력·검색 버튼·Enter 제출, 적용 조건과 이름 필터링을 연결한다.
- **학습:** Form, onFinish, 입력값 타입, 함수 props, 입력 중인 값과 적용 조건, filter·문자열 처리.
- **완료 기준:** 입력만으로 표가 바뀌지 않는다. 제출하면 공백·대소문자 규칙에 따라 부분 검색하고 결과 0건도 안내한다.
- **확인 질문:** 아직 제출하지 않은 검색어와 표에 적용된 검색어는 어디에 있는가?

### 08-B. 활성 여부와 초기화

- **개발:** 전체·Y·N 조건을 이름과 함께 적용한다. 초기화는 Form과 적용 조건을 모두 기본값으로 돌린다.
- **학습:** 조건 조합, 리터럴 유니온, Form 초기화와 입력값을 state로 중복 관리하지 않는 이유.
- **완료 기준:** 이름+활성 여부, 전체 선택, 초기화, 빈 결과가 맞게 동작한다.

### 09. 페이지 이동과 조회 건수

- **개발:** 별도 Ant Design Pagination으로 페이지당 10건, 현재 페이지, 검색된 총 건수를 연결한다. 검색·초기화와 1페이지 이동을 함께 처리하고 잘라 낸 행을 AG Grid에 전달한다. 그리드 자체 페이지 기능은 끈다.
- **학습:** 필터링 후 페이지를 나누는 순서, 계산값과 state, Pagination의 페이지 변경 이벤트.
- **완료 기준:** 25건의 1·2·3페이지, 검색 후 건수, 2페이지에서 검색·초기화, 결과 0건이 맞다. 크기 변경 UI는 제공하지 않는다.
- **범위:** 여기까지는 UI에서 전체 배열을 계산한다. 10-A에서 계산 위치를 옮기며 두 방식을 동시에 유지하지 않는다.

## 10–11: 조회 경계와 비동기

### 10-A. 조회 조건과 결과의 경계

- **개발:** users 전용 UserListQuery·UserListResult를 정의한다. 검색·페이지 계산을 api/queryUsers.ts의 동기 함수로 옮기고 화면에는 items·total만 전달한다.
- **학습:** 함수 입력·반환 타입, 순수 함수, total과 현재 페이지 행 수의 차이.
- **완료 기준:** 기존 사용자 동작을 유지한다. 조회 함수가 검색 후 페이지를 나누고 표는 다시 filter·slice하지 않는다. 범위 밖 페이지는 빈 items와 정확한 total을 반환한다.
- **범위:** Promise·Effect·HTTP는 추가하지 않는다. 가상 배열은 이 중간 단계에만 페이지에서 조회 함수로 전달하고 10-B에서 API 모듈로 옮긴다.

### 10-B. 비동기 조회·로딩·정리

- **개발:** userApi.ts가 원본 데이터를 소유하고 getUsers(query)를 제공한다. 짧은 지연 뒤 Promise로 결과를 반환한다. 페이지의 직접 배열 import를 제거하고 적용 조건·페이지를 기준으로 Effect에서 조회한다.
- **학습:** Promise·async/await → 결과·로딩 state → Effect 의존성·정리 순서로 설명한다. 이전 응답을 무시하는 최소 정리를 함께 구현한다.
- **완료 기준:** 진입·검색·페이지 이동에 로딩 후 올바른 결과가 보인다. 기본 오류 안내로 예외를 처리한다. 화면 이탈·이전 요청의 성공/오류/종료가 최신 상태를 덮지 않는다.
- **범위:** 상세 실패 주입·재시도는 11이다. 의존성 경고를 억제하거나 StrictMode를 끄지 않는다. 분량이 크면 구현 전 이 작업을 더 작게 계획한다.
- **Axios와의 관계:** 이 단계는 메모리의 데이터를 반환하는 모의 API이므로 HTTP 요청과 Axios 설치를 포함하지 않는다. Promise·async/await와 조회 상태 처리는 이후 Axios 연결에서도 활용한다.

### 10-C. 응답 순서와 조회 계약 확인

- **작업:** 모의 지연으로 이전 요청이 나중에 끝나는 경우, 빠른 검색·페이지 변경, 조회 중 이탈, StrictMode 추가 실행, 2·3페이지를 확인한다.
- **학습:** 요청과 응답 순서의 차이, 결과 무시와 실제 요청 취소의 차이.
- **완료 기준:** 최신 목록·total·로딩만 남고 이중 페이지 처리가 없다. 반환 객체를 수정해도 모의 원본이 바뀌지 않는다. 재현 방법을 채팅으로 안내한다.
- **범위:** 정리는 10-B에 구현하고 이 작업은 집중 검증·보완한다.

### 11. 조회 오류와 재조회

- **개발:** 명시적인 모의 실패·해제 방법을 제공하고 검색으로 다시 조회한다. 기본 실행은 정상이다.
- **학습:** try/catch/finally, unknown·타입 좁히기, 대기·성공·빈 결과·실패 구분.
- **완료 기준:** 실패 시 로딩이 끝나고 실패를 0건으로 안내하지 않는다. 이전 목록을 최신 결과처럼 보여 주지 않으며 조회만 재시도해 복구한다.
- **안내:** 실패 설정 위치·켜기/끄기·재시도 순서와 결과를 채팅으로 안내한다. 이후 저장·삭제 실패도 같은 형식으로 안내한다.

## 12–15: 입력과 변경

### 12-A. 등록 모달 입력과 취소

- **개발:** 등록 버튼, UserFormModal 열기·닫기, 직접 입력하는 ID·이름·이메일·부서·활성 여부 입력을 만든다. 활성 여부 기본값은 Y다.
- **학습:** 모달 열림 state, Form 입력값 타입, 필수·선택 입력.
- **완료 기준:** 취소 후 재열기에 기본값이 보인다. 저장 미연결을 명시하며 성공 안내를 표시하지 않는다.

### 12-B. 입력 검증과 재열기

- **개발:** 공백뿐인 ID·이름, 빈 필수값·이메일을 검증하고 입력값을 정리한다. 재열기 때 입력·오류를 초기화한다.
- **학습:** 검증 규칙, 제출 가능한 값, 초기값과 현재 입력값의 차이.
- **완료 기준:** 잘못된 입력을 제출하지 않고 이전 오류가 남지 않는다. 유효한 입력까지 확인하되 저장 미연결을 명시한다.

### 13-A. 등록 저장과 목록 갱신

- **개발:** createUser와 저장 이벤트를 연결한다. API에서 직접 입력한 ID·필수값·형식·중복 ID 및 이메일을 검사한다. 성공 후 모달을 닫고 조건을 유지한 1페이지를 다시 조회한다.
- **학습:** User와 UserFormValues의 역할, 비동기 이벤트, 배열·객체를 직접 변경하지 않는 방식.
- **완료 기준:** 정상 등록, 공백·대소문자를 무시한 중복 이메일, 저장 중 반복 제출·닫기 방지, 실패 시 입력 보존이 맞다. 저장 성공 후 조회 실패는 별도로 안내한다.
- **범위:** 데이터 보존 범위를 화면에 안내한다. 기본 정확성은 여기서 구현하고 13-B에서 집중 확인한다.

### 13-B. 저장 실패와 재조회 실패 구분

- **작업:** 저장 자체 실패와 저장 성공 후 조회 실패를 각각 재현하고 처리·문구를 검증한다.
- **학습:** 변경 요청과 조회 요청의 성공 여부가 다를 수 있다는 점.
- **완료 기준:** 저장 실패 시 입력 유지, 성공 후 조회 실패 시 조회만 재시도, 복구 후 등록 데이터가 한 번만 존재한다. 검색 조건에 맞지 않는 등록도 확인한다.
- **안내:** 실패 주입·해제와 데이터 확인 방법을 채팅으로 안내한다.

### 14-A. 수정 대상과 모달 값

- **개발:** 작업 열의 수정 버튼으로 대상 값을 같은 모달에 채운다. 등록·수정의 제목·기본값·검증 상태를 구분한다.
- **학습:** 선택 객체·null·타입 좁히기, Form 값 갱신.
- **완료 기준:** 연속 대상 선택·수정 취소 후 등록에서 값과 오류가 섞이지 않는다. 수정 저장 미연결을 명시하며 등록 요청이 대신 호출되지 않는다.

### 14-B. 수정 저장

- **개발:** updateUser(id, values)에 오류·중복 제출·성공 후 재조회 규칙을 적용한다.
- **학습:** ID로 대상 찾기, 객체 전개·map, 같은 입력과 다른 저장 동작.
- **완료 기준:** ID 유지·대상만 변경·자기 이메일 유지 성공·타인 중복 실패·입력 보존·조건 유지·1페이지 재조회가 맞다. 모의 실패도 재현한다.

### 15-A. 삭제 대상 확인과 취소

- **개발:** 현재 페이지의 행을 다중 선택하고 대상 이름을 보여 주는 일괄 삭제 확인 UI를 만든다.

- **완료 기준:** 페이지 전환 때 선택을 초기화하고, 확인 팝업에서 대상을 확인할 수 있다. 취소 시 데이터가 유지되며 삭제 미연결을 명시한다.

### 15-B. 삭제 실행과 유효 페이지

- **개발:** 선택된 여러 ID를 deleteUsers로 전달해 한 번에 삭제하고, 진행·실패 안내·반복 실행 방지·삭제 후 조회를 연결한다. total로 마지막 페이지를 계산하고 필요하면 유효 페이지를 다시 조회한다.
- **학습:** Promise<void>, 변경 후 조회, 총 건수에 따른 페이지 보정.
- **완료 기준:** 대상만 삭제·실패 시 유지·마지막 페이지 마지막 행·전체 0건·성공 후 조회 실패에서 조회만 재시도가 맞다.
- **범위:** 실제 삭제 연결부터 페이지 보정을 포함하며 깨진 빈 페이지를 다음으로 미루지 않는다.

## 검증 방법

변경에 맞는 확인만 한다. 코드 변경에는 lint·build와 브라우저 확인, 문서 변경에는 파일·링크·현재 코드와의 일치·단계 선후 관계를 확인한다. 성공한 검사를 이유 없이 반복하지 않는다.

자동 테스트 도구는 19부터 필요한 검사와 함께 도입한다. 그전에는 단계별 실행 확인과 명시적 실패 재현을 한다. 더 일찍 자동 검증할 필요가 생기면 이유와 범위를 계획에 반영한다. 코드 검사 성공을 브라우저 성공으로 표현하지 않는다.

| 기존 명령 | 역할 |
| --- | --- |
| npm.cmd run dev | Vite 개발 서버 |
| npm.cmd run lint | ESLint 코드 검사 |
| npm.cmd run build | tsc -b로 타입 검사 후 Vite 배포용 빌드 |
| npm.cmd run preview | 로컬 빌드 결과 확인; 실제 공개 배포와 별개 |

브라우저 검증에는 환경(dev/preview/배포), 주소·크기, 동작, 기대·실제 결과를 채팅으로 안내한다. 모의 실패는 설정·해제 방법을 채팅으로 안내하고 버그 수정 후 관련 동작을 다시 확인한다.

| 조회 | 연속 검색·페이지 변경·이탈 | 이전 결과·오류·종료가 최신 상태를 덮지 않음 |
| 등록 | 필수값·공백·이메일·중복·정상 저장 | 오류·입력 보존·고유 ID·조건 유지·1페이지 |
| 수정 | 대상 전환·수정 후 등록·자기/타인 이메일 | 입력·오류 분리, ID 유지·대상만 변경 |
| 변경 | 반복 제출·저장 성공 후 조회 실패 | 중복 방지, 조회만 재시도 |
| 삭제 | 취소·확인·반복·실패·재조회 실패 | 대상만 삭제, 실패 시 유지, 삭제 재실행 안 함 |

## 학습을 이어가는 방법

JSP의 서버가 요청마다 HTML을 만드는 경험과 비교하되, React에서는 브라우저의 URL·이벤트·상태가 렌더링을 어떻게 바꾸는지 현재 코드로 설명한다.

사용자 동작 → 이벤트 → 상태·데이터 → 화면 변화를 설명해 본다. 타입 오류는 기대한 값과 실제 값을 비교하고, 비동기 오류는 어떤 요청이 실패했으며 사용자가 다음에 무엇을 할 수 있는지 살핀다.

같은 단계의 작은 변경안을 말로 설명하거나 디버거로 값을 따라가며 이해를 확인할 수 있다. 별도 연습 기능이나 다음 구현은 요청 없이 추가하지 않는다.
