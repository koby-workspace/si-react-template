## 한 작업의 진행 방식

1. 현재 코드와 진행 위치를 읽고 이번에 바뀔 사용자 동작 하나를 짧게 설명한다.
2. AI가 필요한 파일 수정·개발 명령을 실행한다. 처음 쓰는 명령·옵션과 필요한 새 문법은 이유와 함께 설명한다.
3. 사용자 동작 → 이벤트 → 상태·데이터 → 화면 변화를 실제 변경 코드로 연결한다.
4. 변경에 맞는 코드 검사와 실제 실행을 구분해 확인하고 결과를 기록한다.
5. 사용자는 코드를 이해하고 질문한다. 확인 질문의 답변 제출을 강제하지 않는다.
6. 실제 누적 변경에 맞는 한글 커밋 메시지를 제안한다. 사용자는 VS Code에서 변경 목록과 최신 수정의 스테이징 여부를 확인하고 직접 커밋한다.

다음 작업은 사용자가 명시적으로 요청할 때 시작한다. 설명할 내용이 너무 많으면 기능 단위를 다시 나누되, 잘못된 성공 안내·처리되지 않은 오류를 남기고 완료라고 하지 않는다.

**작업 기록 형식:** 변경 파일·사용자 동작 / 필요한 개념·설계 이유 / 코드 검사 명령·결과 / 브라우저 환경·시나리오·결과 / 미확인·남은 문제 / 다음 작은 작업. 커밋·스테이징 완료 여부는 확인된 사실만 기록한다.

미래 작업의 완료 체크는 해당 완료 기준과 검증을 충족했을 때만 한다. 구현·코드 검사만 끝났다면 브라우저 미확인을 별도로 남긴다. 기존 01–06 기록은 당시 이력으로 보존하며, 옛 Left 너비나 라우트·검색 입력을 현재 구현으로 읽지 않는다.

## 기존 구현 기록

### 2026-10-03 AG Grid Community 기준 확정과 사용자 목록 교체

사용자 요청에 따라 기본 그리드를 AG Grid Community로 확정했다. 향후에도 유료 전환·패키지·라이선스·평가판 도입은 없으며 부족한 기능은 필요한 단계에서 직접 개발한다. Ant Design은 기본 UI를 계속 담당한다. 기존 06단계의 Ant Design Table 기록은 당시 이력이다.

`UserPage`는 `ColDef<User>[]`, `AgGridReact<User>`, `rowData`, `getRowId`를 사용하고 `ClientSideRowModelModule`만 등록한다. 기존 5개 열·25건·Y/N·빈 부서의 `-`와 데이터 순서를 유지한다. 자동 높이로 Content 세로 스크롤을 사용하며 열의 최소 너비 합계보다 좁으면 그리드 내부에서 가로 스크롤한다. 페이지 나누기·정렬·열 크기 변경·열 이동은 끈다. `getGridTheme`은 기존 공통 팔레트로 5개 테마와 light/dark를 연결한다.

07의 표 분리 대상은 AG Grid이며, 09에서는 별도 Ant Design Pagination으로 페이지 상태를 제어한다. 10 이후 조회한 `items`를 그리드에 그대로 전달하고 중복 페이지 계산을 하지 않는다. 다음 학습 단계는 시작하지 않았으며 진행 위치는 06-V를 유지한다.

**코드 검사:** `ag-grid-community`와 `ag-grid-react` 36.2.0 설치. `npm.cmd run lint`와 `npm.cmd run build` 통과. JS 1,321.70kB(gzip 400.68kB)로 기존 500kB 초과 경고가 남는다. Enterprise 패키지는 의존성에 없다.

**실제 실행:** 내장 브라우저의 `/users`에서 5개 열과 25건, Y/N, 빈 부서의 `-`, 페이지 UI 없음 확인. 5개 테마×light/dark의 그리드 배경·헤더·글자색과 행 유지 확인. 1280×720·1024×768에서 페이지 가로 넘침 없이 표시하고, 900×768에서는 그리드 내부 가로 스크롤로 활성 여부 열에 접근했다. Content 세로 스크롤로 마지막 사용자에 접근하고 메뉴 접기·펼치기 및 새로고침 시 Classic Blue·light 초기화도 확인했다. 설치 전에 실행 중이던 Vite의 모듈 탐색 오류는 개발 서버 갱신으로 해소했으며 이후 콘솔 오류·경고는 없다. 전체 라우팅·키보드 접근성 검증은 06-V에 남긴다.

### 2026-10-02 테마 아이콘을 전환할 모드 기준으로 조정

후속 요청으로 `TopBar`의 아이콘 조건을 `isDarkMode ? <SunOutlined /> : <MoonOutlined />`로 바꿨다. 현재 light에서는 다크로 전환하는 달, dark에서는 라이트로 전환하는 태양을 표시한다. 기존 `title`·`aria-label`과 아이콘이 모두 전환할 모드를 안내한다. README와 설계 문서도 같은 기준으로 수정했다. 이전 기록의 현재 모드 기준 아이콘 설명은 당시 구현 이력이다. `npm.cmd run lint` 통과. 기존 두 아이콘의 표시 조건만 바꾼 수정이므로 빌드는 다시 실행하지 않았다. 실제 브라우저에서 아이콘 표시와 클릭 확인은 대기다.

### 2026-10-02 테마 전환 버튼을 달·태양 아이콘으로 변경

후속 요청으로 `TopBar`의 텍스트·Switch를 Ant Design 아이콘 버튼으로 변경했다. 현재 dark 모드에서는 `MoonOutlined`, light 모드에서는 `SunOutlined`를 표시한다. `onClick={() => onThemeChange(!isDarkMode)}`는 클릭할 때 현재 boolean 값을 반전하여 부모의 상태 변경 함수에 전달한다. 아이콘은 현재 상태를 표현하고, `title`과 `aria-label`은 전환할 모드를 안내한다. CSS에서 메뉴 버튼과 같은 40×40px 크기·18px 아이콘을 적용하고 오른쪽 배치를 유지했다. 기존 아이콘 패키지를 사용하며 README와 설계도 갱신했다. 코드 검사: npm.cmd run lint 통과. build는 캐시 쓰기 권한 오류 후 승인받아 재실행하여 통과했다. JS 청크 855.01kB로 기존 500kB 초과 경고가 남아 있다. 실제 브라우저 클릭·아이콘 표시 확인은 대기다. 다음 학습 단계는 시작하지 않았다.

### 2026-10-02 light / dark 모드 전환

사용자 요청으로 06-V 전에 테마 전환 한 작업을 추가했다. `src/App.tsx`에 boolean `isDarkMode` 상태와 `ConfigProvider`를 두고, `AppLayout`을 통해 `TopBar`의 `Switch`에 상태와 변경 함수를 전달했다. `checked`는 현재 상태를 표시하고 `onChange`는 새 boolean 값을 상태 변경 함수에 전달한다. 모든 경로보다 위에 상태가 있어 화면 이동 시 유지되며 새로고침하면 기본 light로 초기화한다. 저장·시스템 테마 감지·새 의존성은 추가하지 않았다.

`AppLayout`, `TopBar`, `NotFoundPage`는 `theme.useToken()`으로 현재 테마의 글자색·배경색을 읽는다. CSS의 고정 흰색과 메뉴 버튼의 고정 hover 색을 제거하여 기본 버튼 테마를 사용한다. 본문 링크는 `color: inherit`으로 부모의 글자색을 물려받고 기존 밑줄로 링크임을 표시한다. Top의 스위치 영역은 `margin-left: auto`로 남은 가로 공간을 왼쪽 여백으로 사용하여 오른쪽에 놓는다. `colorScheme`은 브라우저 기본 UI(스크롤바 등)에 현재 모드를 알리는 React 인라인 스타일 속성이다. Ant Design 컴포넌트의 색은 `theme.algorithm`이 담당한다. 설계 문서와 README에도 동작을 반영했다.

코드 검사: `npm.cmd run lint` 통과. 첫 `npm.cmd run build`는 TypeScript 캐시 쓰기 권한 오류로 중단됐고, 승인 후 재실행하여 통과했다. JS 청크는 859.66kB이며 기존 500kB 초과 경고는 남아 있다.

실행 확인: `npm.cmd run dev -- --host 127.0.0.1`로 개발 서버 시작 성공. Codex 내장 브라우저에서 탭 생성 후 세션 연결 오류가 발생했고 탭 목록도 비어 있어 실제 화면은 확인하지 못했다. light → dark → light 전환, 홈·대시보드·사용자 표의 가독성, 메뉴 이동 후 모드 유지, 접기·펼치기, 키보드로 스위치 조작, 새로고침 후 light 초기화는 확인 대기다. 없는 주소의 dark 표시는 앱을 새로 불러오지 않는 뒤로·앞으로 이동으로 확인해야 한다. 진행 위치는 **06-V**로 유지하며 다음 단계는 시작하지 않았다.

### 2026-10-02 공통 레이아웃의 Outlet 위치 변경

사용자 요청에 따라 `src/App.tsx`의 부모 Route를 `element={<AppLayout />}`로 간소화했다. `src/layout/AppLayout.tsx`는 Content 안에 `Outlet`을 직접 배치하며, 사용하지 않는 `children` props 타입과 `ReactNode` import를 제거했다. App은 경로 연결, AppLayout은 페이지 표시 위치를 담당한다. URL·공통 화면 틀·메뉴 접기 로직은 유지했다. 설계 문서에도 현재 구조를 반영했다. 다음 학습 단계는 시작하지 않았으며 진행 위치는 06-V를 유지한다.

`npm.cmd run lint`는 통과했다. 첫 build는 TypeScript 캐시 쓰기 권한 오류로 중단되어 승인 후 재실행했고 통과했다. 기존 500kB 초과 청크 경고는 남아 있다. 이번에는 브라우저 실행 확인을 수행하지 않았으므로 화면 이동과 메뉴 접기의 실제 동작은 확인 대기다. `source-guide.md`는 06단계 당시 소스 참고서이므로 기존 children 설명을 보존하며, 현재 구현과의 차이는 이 기록과 실제 소스로 확인한다.

| 24. 공개 전 품질 | 화면·한국어·키보드 → 번들·초기 로딩 → 근거 있는 개선 하나 | 결과·제한 기록, 조기 최적화 목적의 확장 없음 |
| 25. 검사 자동화 | 기존 명령의 CI 설정 → 실제 실행 확인 | 설치·lint·타입·빌드·도입한 테스트 결과 확인 |
| 26. 공개 데모 | 호스팅 선택·설정 → 배포 → 직접 URL·새로고침·시연 확인 | 백엔드 없이 주요 동작, 필요한 SPA 경로 처리 |
| 27. 포트폴리오 | README·대표 화면 → 짧은 시연 → 설계·검증 근거·이력서 설명 | 타인이 실행·평가 가능, 실제 결과와 설명 일치 |

실제 백엔드는 공개 이후 별도 확장이다. 인증·서버 오류·페이지 계약이 정해지면 작게 나누며, 현재 목표 완성을 서버 개발 때문에 미루지 않는다.

**향후 Axios 학습 순서:** 설치와 사용자 목록 HTTP 조회 하나 → 기능별 API 함수에서 응답 본문을 화면용 타입으로 변환 → 필요한 기본 주소·타임아웃·취소·오류 처리 → 등록·수정·삭제 연결. 각 화살표는 별도 작은 작업으로 진행하고, 인터셉터·인증·자동 재시도는 실제 요구가 생길 때 다룬다. 사용하지 않는 Axios 설정이나 의존성을 미리 추가하지 않는다.

## 검증 방법

변경에 맞는 확인만 한다. 코드 변경에는 lint·build와 브라우저 확인, 문서 변경에는 파일·링크·현재 코드와의 일치·단계 선후 관계를 확인한다. 성공한 검사를 이유 없이 반복하지 않는다.

자동 테스트 도구는 19부터 필요한 검사와 함께 도입한다. 그전에는 단계별 실행 확인과 명시적 실패 재현을 한다. 더 일찍 자동 검증할 필요가 생기면 이유와 범위를 계획에 반영한다. 코드 검사 성공을 브라우저 성공으로 표현하지 않는다.

| 기존 명령 | 역할 |
| --- | --- |
| npm.cmd run dev | Vite 개발 서버 |
| npm.cmd run lint | ESLint 코드 검사 |
| npm.cmd run build | tsc -b로 타입 검사 후 Vite 배포용 빌드 |
| npm.cmd run preview | 로컬 빌드 결과 확인; 실제 공개 배포와 별개 |

브라우저 검증에는 환경(dev/preview/배포), 주소·크기, 동작, 기대·실제 결과를 기록한다. 모의 실패는 설정·해제 방법을 기록하고 버그 수정 후 관련 동작을 다시 확인한다.

**2026-10-02:** AGENTS.md에 JSP·백엔드 배경, Vite·Ant Design 포함 목표, 백엔드 없는 시연·향후 연결·포트폴리오 목적을 반영했다. project-roadmap.md에 업무 완성·재사용 검증·공개 기준을 추가했다. 설계의 조회를 조건·페이지 → items·total 계약으로 변경하고 상태·동시 조회·저장·삭제 규칙을 맞췄다. 계획에 06-V, 작은 하위 작업과 후속 순서를 추가했다. ## 학습을 이어가는 방법

JSP의 서버가 요청마다 HTML을 만드는 경험과 비교하되, React에서는 브라우저의 URL·이벤트·상태가 렌더링을 어떻게 바꾸는지 현재 코드로 설명한다.

사용자 동작 → 이벤트 → 상태·데이터 → 화면 변화를 설명해 본다. 타입 오류는 기대한 값과 실제 값을 비교하고, 비동기 오류는 어떤 요청이 실패했으며 사용자가 다음에 무엇을 할 수 있는지 살핀다.

같은 단계의 작은 변경안을 말로 설명하거나 디버거로 값을 따라가며 이해를 확인할 수 있다. 별도 연습 기능이나 다음 구현은 요청 없이 추가하지 않는다.
