# 단계별 개발·학습 계획

## 기준과 진행 위치

[1차 프로토타입 설계](./prototype-design.md)를 작은 작업으로 나눈 계획이다. 단계 수는 기능 규모보다 설명·검토 단위를 작게 유지하기 위해 정했다. 한 번에 한 단계만 구현한다. 실제 변경이 너무 많으면 그 단계만 더 작게 나누고, 순서 변경이 필요하면 이유와 계획을 갱신한다.

| 항목 | 현재 내용 |
| --- | --- |
| 이번 작업 | 02. 레이아웃 컴포넌트 분리 구현, 코드 검사·빌드 통과 (브라우저 확인 대기) |
| 확인한 출발점 | React + TypeScript + Vite, Ant Design 설치, 이름 입력·초기화 화면 |
| 다음 개발 단계 | **03. Left 접기·펼치기** |
| 완료한 개발 단계 | 01–02 구현·코드 검증 완료, 실제 배치는 브라우저 확인 필요 |

위 표는 진행 기록이므로 이 문서에서 관리한다. `AGENTS.md`에는 지속 지침만 둔다. 현재 개발 단계가 끝나면 이 표와 해당 체크박스를 갱신한다. 미래 단계의 코드나 설정은 미리 추가하지 않는다.

## 한 단계의 진행 방식

1. 현재 코드와 설계·계획을 읽고 이번 단계의 작업과 사용자 동작을 짧게 설명한다.
2. AI가 필요한 파일 수정과 명령 실행을 수행한다. 새로 실행하는 개발 명령은 의미를 설명한다.
3. 변경한 코드를 바탕으로 문법·동작·도입 이유와 필요한 선행 개념을 설명한다.
4. 단계의 완료 기준에 맞게 검증하고, 코드 검사와 브라우저 실행 확인을 구분해 결과를 기록한다.
5. 사용자는 코드를 이해하고 질문한다. 아래 확인 질문은 이해를 돕는 도구이며 답변 제출을 강제하지 않는다.
6. 계획의 진행 위치를 갱신하고 실제 변경에 맞는 한글 커밋 메시지를 제안한다. 사용자가 VS Code에서 최신 변경을 스테이징하고 커밋한다.

사용자가 다음 단계 진행을 명시적으로 요청할 때만 다음 구현으로 넘어간다. 설명이나 질문만으로 다음 단계를 시작하지 않는다. 브라우저 확인을 수행하지 못한 경우에는 그 사실과 사용자가 확인할 동작을 명시한다.

## 01–05: 화면 틀과 이동

### 01. Top / Left / Content 배치

- [ ] 완료
- **개발:** 현재 `App.tsx`에 Ant Design `Layout`을 조합한다. Top에 프로젝트 이름, Left에 영역 표시, Content에 기존 검색 화면을 배치한다. 최소 CSS만 추가하며 메뉴 동작은 아직 구현하지 않는다.
- **학습:** JSX 중첩, 컴포넌트 조합, 라이브러리 컴포넌트의 props. 추가한 CSS 속성과 값은 실제 배치 결과로 설명한다.
- **완료 기준:** Top이 전체 너비이고, 아래에 Left와 Content가 좌우로 보인다. 기존 입력·초기화가 계속 동작한다.
- **확인 질문:** 안쪽 `Layout`이 필요한 이유와 기존 검색 화면을 넣은 위치를 설명할 수 있는가?

**진행 기록:** `App.tsx`에 `Layout.Header`, 안쪽 `Layout`, `Layout.Sider`, `Layout.Content`를 조합했다. Top에는 프로젝트 이름, Left에는 영역 표시, Content에는 기존 이름 입력·초기화 화면을 배치했다. `src/styles.css`에 화면 높이, 여백, Top 글자색과 Content 스크롤을 추가했다. `npm.cmd run lint`와 `npm.cmd run build`는 통과했다. 브라우저 실행 확인은 수행하지 못했으므로 완료 체크는 보류한다. 1280×720과 1024×768에서 Top 전체 너비 및 Left/Content 좌우 배치, 이름 입력 반영, 초기화 후 빈 입력과 버튼 비활성화를 확인해야 한다.

### 02. 레이아웃 컴포넌트 분리

- [ ] 완료
- **개발:** `AppLayout`, `TopBar`, `SideMenu`로 공통 틀을 분리한다. `AppLayout`은 `children`으로 Content에 표시할 내용을 받는다.
- **학습:** import/export, props 타입, `children`, `ReactNode`, `import type`. `.ts`와 `.tsx`의 용도도 필요한 만큼 짚는다.
- **완료 기준:** 파일을 나눠도 화면과 검색 동작이 동일하며, `AppLayout`에 사용자 검색 로직이 들어가지 않는다.
- **확인 질문:** 다른 업무 화면을 Content에 넣으려면 어떤 부분을 바꾸면 되는가?

**진행 기록:** 요청 시점의 코드에는 검색 입력 대신 `Content 영역` 문구가 표시되어 있었다. 현재 표시 내용과 CSS를 유지하면서 공통 틀을 `src/layout/AppLayout.tsx`, `TopBar.tsx`, `SideMenu.tsx`로 분리했다. `AppLayout`은 `children: ReactNode`로 Content 내용을 받으며, `App.tsx`에서 내용을 전달한다. 사용하지 않는 검색 state, 초기화 함수와 import를 제거했다. `npm.cmd run lint`와 `npm.cmd run build`는 통과했다. 브라우저 실행 확인은 수행하지 못했으므로 완료 체크는 보류한다. 브라우저에서 Top의 프로젝트 이름, Left 영역, Content 영역이 이전과 같은 위치에 표시되는지 확인해야 한다. 현재 화면에는 검색 입력·초기화가 없으므로 해당 동작은 검증 대상에 포함하지 않았다.

### 03. Left 접기·펼치기

- [ ] 완료
- **개발:** `AppLayout`에 접기 상태를 두고 Top 버튼으로 Left 너비를 바꾼다. 버튼과 Left에 필요한 props를 전달한다.
- **학습:** boolean state, 상태를 함께 쓰는 컴포넌트의 공통 부모, 함수 props, 이전 상태를 사용하는 갱신.
- **완료 기준:** 버튼을 반복해 눌러도 Left와 Content 너비가 맞게 바뀌며, 버튼의 조작 의미가 표시된다.
- **확인 질문:** Top과 Left가 각각 접기 state를 가지면 어떤 문제가 생길 수 있는가?

### 04. URL로 홈·사용자 화면 이동

- [ ] 완료
- **개발:** React Router를 설치한다. 기존 검색 화면을 `UserPage`로 옮기고 작은 `HomePage`를 만든다. 공통 틀 아래에 `/`, `/users`를 연결하고 Left에서 이동한다.
- **학습:** URL과 화면의 관계, `BrowserRouter`, `Routes`, `Route`, `Outlet`, `Link`. 일반 새로고침 이동과 앱 내부 화면 이동의 차이.
- **완료 기준:** 메뉴를 누르면 URL과 Content가 함께 바뀌고 공통 틀은 유지된다. 주소 직접 입력과 브라우저 뒤로 가기가 동작한다.
- **확인 질문:** 메뉴를 클릭할 때 Content를 바꾸는 기준은 어떤 값인가?

### 05. 현재 메뉴와 없는 주소 안내

- [ ] 완료
- **개발:** `useLocation`으로 메뉴 선택을 URL에 맞춘다. 없는 주소는 공통 틀 안의 `NotFoundPage`에서 안내하고 홈 링크를 제공한다.
- **학습:** 조건에 따른 값 계산, 별도 state 없이 현재 값에서 표시를 결정하는 방식, `*` 경로.
- **완료 기준:** 뒤로·앞으로 가기에도 메뉴 선택이 맞는다. 없는 주소에서는 오류 안내가 보이고 홈으로 돌아갈 수 있다.
- **확인 질문:** 선택 메뉴를 state로 따로 저장하지 않는 이유는 무엇인가?

## 06–09: 목록과 검색

### 06. 사용자 타입과 목록 표

- [ ] 완료
- **개발:** `UserStatus`, `User`, 가상 사용자 25건 이상을 정의하고 Ant Design `Table`에 표시한다. 우선 페이지 나누기 없이 표를 확인한다. 앱의 `strict` 검사를 켜고 발생한 타입 오류를 함께 해결한다. 검색 입력은 유지하되 실제 필터 연결은 08에서 한다.
- **학습:** 객체·배열 타입, 문자열 리터럴 유니온, 타입 추론, `strict`, `Table<User>`의 제네릭 사용, `rowKey`. 타입 검사가 실행 중 데이터 검증을 대신하지 않는다는 점.
- **완료 기준:** 필드에 맞는 열과 활성·비활성 표시가 보이고, ID로 행을 식별한다. 엄격한 타입 검사에서도 빌드가 통과한다.
- **확인 질문:** `status: string` 대신 두 값만 허용하면 어떤 잘못을 미리 찾을 수 있는가?

### 07. 사용자 표의 역할 분리

- [ ] 완료
- **개발:** 표 표시를 `UserTable`로 옮기고 `User[]`를 props로 받는다. 데이터를 소유하는 페이지와 데이터를 표시하는 표의 역할을 나눈다.
- **학습:** 배열 props의 타입, 부모에서 자식으로 데이터 전달, 컴포넌트를 나눌 기준. 수정·삭제용 props는 아직 추가하지 않는다.
- **완료 기준:** `UserTable`이 사용자 데이터를 직접 만들거나 변경하지 않으며 기존 표와 같은 결과를 보인다.
- **확인 질문:** 사용자 목록이 바뀌면 표는 어떤 경로로 새 데이터를 받는가?

### 08. 실제로 동작하는 검색 Form

- [ ] 완료
- **개발:** 기존 입력을 이름·상태 조건이 있는 `UserSearchForm`으로 발전시킨다. 검색·초기화 이벤트를 페이지에 전달하고 목록을 필터링한다.
- **학습:** Ant Design `Form`과 `onFinish`, 입력값 타입, 함수 props, 입력 중인 값과 적용 조건, `filter`·문자열 처리. Form의 입력 관리와 기존 제어 입력 방식의 관계.
- **완료 기준:** 입력만으로 목록이 바뀌지 않는다. 검색 버튼·Enter로 조건이 적용되고 초기화하면 전체 목록으로 돌아온다. 결과 0건을 안내한다.
- **확인 질문:** 검색어를 고치는 동안 표에 적용된 검색어는 어디에 남아 있는가?

### 09. 페이지 이동과 조회 건수

- [ ] 완료
- **개발:** 페이지당 10건과 현재 페이지를 연결하고 검색된 총 건수를 표시한다. 검색·초기화 시 1페이지로 이동한다.
- **학습:** 필터링 후 페이지를 나누는 순서, 계산한 값과 state의 차이, Table의 페이지 변경 이벤트.
- **완료 기준:** 2페이지에서 새 검색을 해도 빈 페이지에 갇히지 않으며, 총 건수는 전체 데이터가 아니라 검색 결과에 맞는다.
- **확인 질문:** 25건 중 검색 결과가 3건이라면 총 건수와 페이지 수는 각각 어떻게 되어야 하는가?

## 10–15: 조회와 입력·저장

### 10. 비동기 모의 조회와 로딩

- [ ] 완료
- **개발:** 초기 데이터 보관과 조회를 `userApi.ts`로 옮긴다. 짧은 지연이 있는 조회 함수를 화면 진입 시 호출하고 로딩을 표시한다. 조회와 화면 표시를 분리한다.
- **학습:** 함수 반환 타입, `Promise`, `async/await`, `useEffect`, 의존성 배열, Effect 정리, `StrictMode`. 선행 개념인 비동기 작업 순서도 실제 조회 흐름으로 설명한다.
- **완료 기준:** 로딩 후 목록이 나타나고 조회 중 화면을 이동해도 이전 결과가 새 화면을 덮지 않는다. 모의 API가 실제 HTTP 요청을 보내지 않는다는 점을 구분한다.
- **확인 질문:** 조회 함수를 컴포넌트 본문에서 매번 호출하면 어떤 일이 생길 수 있는가?

### 11. 조회 오류와 재시도

- [ ] 완료
- **개발:** 조회 실패 안내와 재시도 버튼을 추가한다. 개발용 모의 실패를 명시적으로 켜고 끄는 재현 방법을 이 문서에 기록한다. 기본 동작은 정상으로 유지한다.
- **학습:** `try/catch/finally`, 오류 값의 `unknown`과 타입 좁히기, 로딩·성공·실패 구분. catch에서 무조건 문자열로 가정하지 않는다.
- **완료 기준:** 빈 결과와 실패가 다르게 보이며, 실패 후 로딩이 끝나고 재시도로 정상 목록을 볼 수 있다.
- **확인 질문:** 조회 실패 때 목록을 빈 배열로만 바꾸면 사용자가 무엇을 오해할 수 있는가?

### 12. 등록 입력 모달과 검증

- [ ] 완료
- **개발:** `UserFormModal`에 이름·이메일·부서·상태 입력을 만든다. 열기·취소와 필수값·이메일 형식 검증부터 완성한다. 이 단계에는 실제 등록 저장이 아직 연결되지 않았음을 분명히 한다.
- **학습:** Modal의 열림 상태, Form 입력값 타입, 검증 규칙, 초기값, 폼 초기화. 선택 입력과 필수 입력의 차이.
- **완료 기준:** 빈 이름이나 잘못된 이메일에 오류가 보이고, 취소 후 다시 열면 이전 값과 오류가 남지 않는다. 저장 성공 안내를 미리 표시하지 않는다.
- **확인 질문:** 모달의 열림 상태와 입력값은 각각 누가 관리하는가?

### 13. 등록 저장 연결

- [ ] 완료
- **개발:** 등록 API와 페이지의 저장 처리를 연결한다. API가 ID를 만들고 중복 이메일을 검사한다. 저장 중 중복 제출을 막고, 성공 후 모달을 닫고 목록을 다시 조회한다. 저장 실패와 저장 후 재조회 실패를 재현하는 방법도 기록한다.
- **학습:** 데이터와 입력값 타입의 차이, 필요한 경우 `Omit`, 타입이 있는 제출 함수, 이벤트의 비동기 처리, 배열을 직접 변경하지 않는 방식.
- **완료 기준:** 등록한 사용자가 검색 조건에 맞으면 목록에 나타난다. 중복 이메일 실패 시 입력이 유지된다. 저장 성공 뒤 조회 실패는 조회만 재시도한다.
- **확인 질문:** 사용자가 등록 Form에서 ID를 입력하지 않아도 되는 이유는 무엇인가?

### 14. 기존 사용자 수정

- [ ] 완료
- **개발:** 행의 수정 버튼으로 기존 모달을 열고 선택한 값을 채운다. 같은 입력·검증을 재사용하며 수정 API로 저장한다. 등록과 수정을 오갈 때 값을 초기화하고, 수정 실패 재현 방법을 기록한다.
- **학습:** 선택한 객체와 `null`, 조건별 타입 좁히기, 기존 값으로 Form 채우기, 공통 입력과 다른 저장 동작. 필요한 객체 전개·`map`을 실제 갱신 코드로 설명한다.
- **완료 기준:** 대상 ID가 유지되고 해당 사용자만 바뀐다. 다른 사용자를 연속 수정하거나 수정 후 등록을 열어도 값이 섞이지 않는다. 자기 이메일 그대로 저장할 수 있다.
- **확인 질문:** 수정할 사용자를 배열 순서 대신 ID로 찾는 이유는 무엇인가?

### 15. 확인 후 사용자 삭제

- [ ] 완료
- **개발:** 삭제 확인·취소·진행 표시를 연결한다. 삭제 성공 후 목록을 다시 조회하고 유효한 페이지로 보정한다. 실패 안내를 연결하고 삭제 실패 재현 방법을 기록한다.
- **학습:** 이벤트에 대상 ID 전달, `Promise<void>`, 변경 후 조회, 데이터 개수가 바뀔 때 현재 페이지 처리.
- **완료 기준:** 취소는 데이터를 바꾸지 않는다. 삭제 대상만 사라지고, 마지막 페이지의 마지막 사용자를 삭제해도 목록을 계속 사용할 수 있다.

## 검증 방법

각 단계는 변경에 맞는 확인만 수행한다. 코드 변경 단계에서는 기존 `lint`와 `build` 스크립트를 활용하고, 동작 변화는 브라우저에서 별도로 확인한다. 문서만 수정한 단계는 문서의 내용·링크·단계 순서를 확인한다. 검사 실패가 있으면 완료 체크를 먼저 하지 않고 원인을 해결한다.

새 테스트 도구나 설정은 미리 추가하지 않는다. 반복되거나 중요한 처리에 자동 검증이 필요해지면 해당 단계에서 의미 있는 테스트와 도입 이유를 정한다. 빌드 통과를 브라우저 테스트 통과로 표현하지 않는다.

기존 npm 스크립트의 역할은 다음과 같다. 실제 실행 시 처음 사용하는 명령과 옵션은 별도로 설명한다.

| 명령 | 역할 |
| --- | --- |
| `npm.cmd run dev` | Vite 개발 서버 실행 |
| `npm.cmd run lint` | ESLint 코드 검사 |
| `npm.cmd run build` | `tsc -b`로 TypeScript 검사 후 Vite 배포용 빌드 |
| `npm.cmd run preview` | 빌드된 결과를 로컬 서버에서 확인 |

## 학습 내용을 능숙하게 사용하는 연습

**문서 정비 기록:** 사용자 요청에 따라 README의 Vite 기본 템플릿 안내를 프로젝트 소개, 준비 환경, 의존성 설치, 개발 서버 실행, 코드 검사·빌드·미리보기, 현재 폴더 구조와 설계·학습 문서 링크로 교체했다. 현재 코드와 `package.json`, 설치된 도구의 Node.js 요구사항, 문서 링크를 확인했다. 문서만 변경했으므로 빌드와 브라우저 실행은 다시 수행하지 않았다. 개발 단계의 진행 위치는 유지한다.

각 단계에서 코드를 모두 외우는 대신 **사용자 동작 → 이벤트 → 상태·데이터 변경 → 화면 변화**를 설명해 본다. 타입 오류가 생기면 기대한 데이터 모양과 실제 값을 비교하고, 로딩이나 오류 때 사용자가 보는 화면을 생각한다.

원하면 그 단계 범위 안에서 작은 변경안을 말로 구성해 본다. 예를 들어 08에서는 부서 검색을 넣는 데 필요한 입력값·조건·필터 변경을 설명하고, AI가 사용자의 요청에 따라 실제 수정을 수행한다. 이런 추가 요구가 채택되면 계획도 갱신한다. 별도 연습 기능을 자동으로 구현하지 않는다.

1차 이후에는 같은 틀에 두 번째 업무 화면을 적용하고 실제 API를 연결하면서 재사용 범위·오류 처리·테스트를 이어서 익힌다. 구체적인 다음 범위는 1차 결과를 검토한 뒤 정한다.
