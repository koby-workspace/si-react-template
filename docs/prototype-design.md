# 1차 프로토타입 설계

## 목표와 문서 사용법

다양한 SI 프로젝트에서 출발점으로 사용할 수 있는 Vite + React + TypeScript + Ant Design 프런트엔드를 만든다. 1차 목표는 백엔드 없이 공통 화면 틀과 사용자 관리 한 화면을 끝까지 동작시키는 것이다. 사용자 관리는 목록·검색·입력·검증·저장 흐름을 익히기 위한 대표 기능이며, 다른 프로젝트의 업무 화면으로 교체할 수 있게 공통 틀과 분리한다.

이 문서는 **1차 완료 시점의 설계**다. 현재 구현된 기능 목록이나 미리 생성할 파일 목록이 아니다. 구현 순서와 진행 상태는 [단계별 개발·학습 계획](./learning-plan.md)을 따른다. 필요한 파일과 설정은 해당 단계에서 추가한다.

두 번째 업무 화면으로 재사용성을 확인하고 포트폴리오로 공개하는 범위는 [프로젝트 로드맵](./project-roadmap.md)에서 관리한다. 1차 완료와 최종 포트폴리오 완성을 구분한다.

## 1차 범위

| 영역 | 1차에 완성할 내용 |
| --- | --- |
| 공통 화면 틀 | Top / Left / Content 분리, Left 접기·펼치기, 5개 색상·모양 테마 선택, light / dark 모드 전환 |
| 화면 이동 | 홈·대시보드·사용자 관리 이동, 시스템명 클릭 시 홈 이동, URL에 따른 메뉴 선택, 없는 주소 안내 |
| 사용자 목록 | ID·이름·이메일·부서·활성 여부 표시, 페이지 이동 |
| 검색 | 이름 부분 검색, 활성 여부 Y·N 조건, 검색·초기화 |
| 등록·수정 | 모달 입력, 필수값·이메일 형식 검증, 저장 |
| 삭제 | 대상 이름을 보여 주는 확인, 취소·삭제 |
| 비동기 처리 | 모의 데이터 조회·저장, 로딩·빈 결과·오류·재시도 |
| 공통 표현 | 화면 제목, 작업 성공·실패 안내, 한국어 UI |
| 마무리 | 코드 검사, 빌드, 브라우저 동작 확인, 실행·확인 방법 문서화 |

실제 서버·DB, 로그인·권한, 파일 첨부·엑셀, 다중 탭, 통계 대시보드, 모바일 전용 화면은 이후 범위다. 전역 상태 라이브러리, 데이터 캐시 라이브러리, 범용 CRUD 생성기도 1차에 추가하지 않는다. 현재 기능에서 필요성이 생기면 다음 설계에서 판단한다.

## Top / Left / Content 구조

Top은 화면 전체 너비를 사용하고, 그 아래에 Left와 Content를 좌우로 배치한다.

```text
┌──────────────────────────────────────────────────────────┐
│ Top: 프로젝트 이름 / Left 접기·펼치기 버튼               │
├──────────────┬───────────────────────────────────────────┤
│ Left         │ Content                                   │
│              │                                           │
│ · 홈         │ 화면 제목과 설명                          │
│ · 대시보드   │                                           │
│ · 사용자 관리│ 검색 조건                                 │
│              │ 조회 건수 / 등록 버튼                     │
│              │ 목록 표 / 페이지 이동                     │
│              │                                           │
└──────────────┴───────────────────────────────────────────┘
```

| 영역 | 역할 | 구현 방향 |
| --- | --- | --- |
| Top | 프로젝트 식별과 공통 조작 | `Layout.Header`, 홈으로 이동하는 시스템명 링크, 접기 버튼, 테마 선택 콤보박스, 모드 전환 아이콘 버튼 |
| Left | 업무 화면 이동과 현재 위치 표시 | `Layout.Sider`, `Menu` |
| Content | 선택한 화면의 내용 | `Layout.Content`, 라우트에 맞는 페이지 |

Ant Design은 `Layout` 아래에 `Header`, `Sider`, `Content`와 내부 `Layout`을 조합할 수 있다. 이 구성을 사용한다. [Ant Design Layout 공식 문서](https://ant.design/components/layout/)

초기 기준은 Top 높이 64px, Left 너비 208px, 접은 너비 0px, Content 안쪽 여백 24px이다. Left를 접으면 완전히 숨겨 Content가 아래 영역의 전체 너비를 사용하고, Top 버튼으로 다시 펼친다. 업무용 데스크톱 화면을 대상으로 하며, 1280×720과 1024×768에서 확인한다. 표가 넓으면 표 내부에서 가로 스크롤하고, 내용이 길면 Content가 세로 스크롤한다. Top과 펼쳐진 Left는 화면에 유지한다. CSS는 이 배치와 읽기 쉬운 간격에 필요한 것만 작성한다.

접기 상태는 `AppLayout`이 관리하고 Top의 버튼과 Left에 전달한다. 화면을 이동해도 공통 틀은 유지한다. 인증 기능이 없으므로 Top에 로그인 사용자나 로그아웃 버튼은 넣지 않는다.

### 테마 선택과 light / dark 모드

Top 오른쪽의 모드 버튼 왼쪽 콤보박스에서 Classic Blue, Soft Green, Modern Purple, Minimal Mono, Warm Orange 중 하나를 선택한다. 네이비·녹색·보라색·무채색·주황색 계열로 Top·Left·본문·메뉴 선택 표시·표 헤더를 함께 바꾸며, 컴포넌트 모서리도 테마에 맞춘다. Minimal Mono는 각진 모서리와 그림자 없는 표현을 사용한다. 크기·간격만 줄이는 컴팩트는 선택지에서 제외한다. 글자 크기와 공통 화면 배치는 유지한다.

각 테마는 light / dark를 모두 지원한다. 테마를 바꿔도 현재 모드는 유지되고, 모드를 바꿔도 선택 테마는 유지된다. 기본값은 Classic Blue와 light이며, 두 상태를 모든 경로의 공통 부모인 `App`에서 관리해 화면 이동과 없는 주소에서 돌아올 때 유지한다. 새로고침하면 기본값으로 초기화한다. 저장·시스템 테마 자동 감지는 이번 범위에 포함하지 않는다.

Top 오른쪽의 아이콘 버튼으로 모드를 전환한다. 아이콘은 전환할 모드를 표현하므로 현재 light 모드에서는 달, dark 모드에서는 태양을 표시한다. 버튼의 `title`과 `aria-label`도 클릭 시 전환할 모드를 안내한다. Top·Left·Content·표와 없는 주소 안내에 같은 테마를 적용한다. light에서도 Classic Blue·Modern Purple·Warm Orange의 Top은 진한 색상을 사용하여 테마 특징을 보여 준다.

`src/theme.ts`는 5개 테마의 모드별 색상과 형태를 관리하며 `getAppTheme`으로 `ConfigProvider`에 전달할 설정을 만든다. `theme.algorithm`에는 `defaultAlgorithm` 또는 `darkAlgorithm`을 사용한다. 공통 토큰은 강조색·본문 배경·테두리·모서리, 컴포넌트별 토큰은 Layout·Menu의 색상을 담당한다. AG Grid는 Ant Design 토큰이 자동 적용되지 않으므로 같은 팔레트로 `getGridTheme`에서 Quartz 테마를 만들고 사용자 화면에 적용한다. 직접 작성한 영역은 `theme.useToken()`으로 현재 테마의 글자색·배경색을 읽는다. `Sider`의 `theme="light"`를 유지하고 각 모드의 `lightSiderBg`와 Menu 토큰을 지정해 Left를 표현한다. [Ant Design 테마 공식 문서](https://ant.design/docs/react/customize-theme/), [AG Grid 테마 매개변수](https://www.ag-grid.com/react-data-grid/theming-parameters/)

## 화면과 사용자 동작

홈·대시보드·사용자 관리의 제목과 설명은 `src/components/PageHeader.tsx`로 함께 표시한다. 각 화면이 제목 문자열과 설명 JSX를 전달하며, 공통 컴포넌트는 업무별 조회·저장이나 버튼 동작을 처리하지 않는다. 사용자 관리의 검색 안내와 데이터 초기화 안내는 제목 아래, 검색 폼 위에 둔다. 등록·삭제 버튼은 조회 결과 총 건수 줄 오른쪽에 배치한다.

### 홈 `/`

홈을 앱의 기본 화면으로 사용한다. 프로젝트 안내와 대시보드·사용자 관리 화면으로 이동하는 링크를 보여 준다. Top의 시스템명을 클릭하면 홈으로 이동한다.

### 대시보드 `/dashboard`

홈과 별도로 주요 현황을 모아서 보여 줄 화면이다. UI 이름은 대시보드, 코드 이름은 DashboardPage로 사용한다. 현재 단계에서는 제목과 개발 중이라는 안내를 표시하며, 통계나 차트는 필요한 기능이 정해진 단계에서 추가한다.

### 사용자 관리 `/users`

사용자는 검색 조건을 입력하고 **검색**을 눌러 목록을 좁힌다. 검색 조건은 이름과 활성 여부이며, 활성 여부에는 전체·Y·N이 있다. 이름은 앞뒤 공백을 제거하고 부분 일치로 검색한다. 영문 대소문자는 구분하지 않는다.

입력 중인 조건과 실제 적용된 조건을 구분한다. 입력만으로 표가 바뀌지 않으며, Enter로도 검색할 수 있다. **초기화**는 입력값과 적용 조건을 모두 기본값으로 돌린다. 새 검색과 초기화는 1페이지로 이동한다.

그리드는 AG Grid Community를 사용한다. 1차 완성 시 한 페이지에 10건을 표시하며, 페이지 크기를 바꾸는 UI를 제공하지 않는다. 모의 데이터는 25건 이상 준비해 페이지 이동을 실제로 확인한다. 초기 목록은 가상 데이터의 순서로 고정하고, 새 사용자는 맨 앞에 추가하며 수정은 순서를 바꾸지 않는다. 열은 현재 페이지 전체 선택 체크박스·ID·이름·이메일·부서·활성 여부·작업 순서로 구성한다. 헤더 체크박스는 현재 페이지 행만 선택·해제하며 일부 선택이면 중간 상태를 표시한다. 작업 열에는 수정 버튼만 둔다. 사용자는 현재 페이지에서 여러 행을 체크한 뒤 총 건수 줄의 오른쪽에서 삭제를 누른다. 선택은 페이지 이동·검색 조건 변경·초기화에서 초기화한다. 확인 팝업은 선택 건수와 이름을 보여 주며, 확인하면 모의 API가 선택된 사용자를 한 번에 삭제한다. 취소하면 선택과 데이터가 유지된다. 삭제 실패 시 데이터와 선택을 보존하고, 성공하면 현재 검색 조건으로 다시 조회한다. 결과가 0건이면 1페이지의 빈 결과를 표시하며 현재 페이지가 마지막 페이지를 초과하면 유효한 마지막 페이지로 보정한다. ID는 `getRowId`가 반환하여 행을 식별한다. 목록은 검색된 총 건수를 표시하고 별도 Ant Design Pagination으로 10건씩 이동한다. 검색·초기화는 1페이지로 돌아가며, AG Grid 자체 페이지 기능은 끈다.

**등록**은 빈 입력 모달을 연다. 등록 버튼은 총 건수 줄 오른쪽 끝에 배치한다. ID·이름·이메일·부서·활성 여부 입력, 저장 검증, 취소를 제공한다. 활성 여부 기본값은 Y이며 취소·닫기 후 재열기에는 빈 입력과 Y로 돌아간다. 저장은 필수값·공백뿐인 ID와 이름·이메일 형식을 검사하고 앞뒤 공백을 정리한다. 모의 API는 필수값·이메일·Y/N과 공백·대소문자를 무시한 ID 및 이메일 중복을 검사하고 입력한 ID로 새 사용자를 목록 앞에 추가한다. 실패 시 모달과 입력값을 유지하고 오류를 표시한다. 성공하면 모달을 닫고 등록 완료를 안내하며 적용 조건을 유지한 1페이지를 다시 조회한다. 저장 성공 후 조회 실패는 등록 완료와 목록 조회 실패를 구분해 안내하고 검색으로 조회만 재시도한다. 재열기에는 입력·검증 오류·저장 오류를 초기화한다.

**수정**은 작업 열의 수정 버튼으로 선택한 사용자의 값을 같은 입력 모달에 채운다. ID는 읽기 전용이며 이름·이메일·활성 여부는 필수이고 부서는 선택 입력이다. 이름·이메일·부서는 앞뒤 공백을 제거하며 공백만 있는 이름과 잘못된 이메일은 입력 단계에서 안내한다. 수정 저장은 updateUser(id, values)를 호출하고 ID와 행 순서를 유지한 채 선택한 사용자만 변경한다. 수정 API에서는 중복 이메일을 앞뒤 공백과 영문 대소문자를 무시해 검사하고, 자기 자신의 이메일은 중복으로 취급하지 않는다. 이 중복 판정은 예제의 업무 규칙이며 실제 서버 계약이 생기면 맞춘다.

저장 중에는 중복 제출과 모달 닫기를 막고 진행 상태를 표시한다. 저장 실패 시 입력값을 유지한다. 저장 성공 시 모달을 닫고 목록을 다시 조회한다. 등록·수정 후에는 검색 조건을 유지하면서 1페이지로 이동한다. 조건에 맞지 않는 사용자는 목록에 보이지 않을 수 있다. 모달은 열 때마다 등록 기본값 또는 선택한 사용자 값과 검증 상태를 명시적으로 준비한다. Form의 초기값이 대상 변경만으로 자동 갱신된다고 가정하지 않는다. [Ant Design Form 안내](https://ant.design/components/form/)

**일괄 삭제**는 선택한 사용자 여러 명의 이름·건수를 한 팝업에서 확인한다. 선택이 없으면 실행 버튼을 비활성화한다. 검색 조건 변경과 등록·수정·삭제 성공 시 선택을 지운다. 취소하면 선택과 데이터가 유지된다. 확인하면 deleteUsers에 선택된 ID 배열을 보내며, 모의 API는 요청 전체를 검증한 뒤 원본 데이터에서 한 번에 제거한다. 요청 실패 시 실패를 안내하고 행과 선택을 유지한다. 성공 안내를 닫으면 삭제 요청을 다시 보내지 않고 현재 검색 조건으로 목록을 재조회한다. 이 재조회가 실패하면 삭제 완료와 조회 실패를 구분해 알리고 검색으로 목록만 다시 조회한다. 현재 조회 총 건수에서 삭제 건수를 빼 마지막 페이지를 계산한다. 현재 페이지가 그보다 크면 유효한 마지막 페이지로 옮겨 조회한다. 결과가 0건이면 1페이지의 빈 결과를 표시한다.

### 없는 주소 `*`

없는 주소에서는 Top / Left / Content 틀을 표시하지 않고, 전체 화면에 없는 페이지 안내와 홈 이동 링크를 보여 준다. 홈으로 돌아가면 공통 틀과 홈 메뉴 선택 표시를 다시 보여 준다.

URL과 화면 연결에는 React Router의 Declarative 모드를 사용한다. 기본 화면 전환에 필요한 `BrowserRouter`, `Routes`, `Route`, `Outlet`, `Link`, `useLocation`부터 해당 단계에서 익힌다. [React Router 모드 설명](https://reactrouter.com/start/modes), [라우팅 공식 문서](https://reactrouter.com/start/declarative/routing)

`App.tsx`는 부모 Route의 element로 `AppLayout`을 지정하고 자식 경로를 연결한다. `AppLayout`은 Content 안에 `Outlet`을 직접 배치하여 선택된 자식 페이지를 표시한다.

등록·수정 성공과 조회 실패는 `src/utils/appAlert.ts`의 공통 `appAlert` 객체를 import해 `success`·`error` 함수로 표시한다. ConfigProvider와 Ant Design App 아래에 AppAlertSetup을 한 번 배치한다. 이 컴포넌트가 App.useApp으로 받은 modal API를 useLayoutEffect에서 연결하여 화면의 조회 Effect보다 먼저 준비하며, 제거 시 연결을 해제한다. 연결 전 호출은 명확한 오류로 처리한다. 테마와 팝업 표시는 Ant Design이 담당하며 공통 모듈에는 제목·확인 버튼·가운데 배치·닫기 제한 설정을 모은다. 화면별 훅·팝업 state·Modal JSX는 필요 없다. 팝업의 자동 교체나 화면 이탈 시 자동 닫기는 제공하지 않는다. 순서가 필요한 호출은 `await appAlert.success(...)`처럼 확인을 기다린다. 사용자 등록은 성공 팝업의 확인을 누른 뒤 조건을 유지한 1페이지를 조회하므로, 이후 조회 실패 팝업과 겹치지 않는다. 조회 실패 팝업을 닫아도 이전 목록·총 건수·페이지는 숨기고 조회 결과를 표시할 수 없다는 빈 영역 안내를 유지한다. 검색으로 조회만 다시 시도한다. 등록 성공 후 재조회 실패는 등록 완료·조회 실패를 구분해 안내한다. 등록 Form의 저장 실패는 입력을 수정할 수 있도록 모달 안의 Alert를 유지한다.

## 데이터와 상태

사용자 데이터의 기본 모양은 다음과 같다. 이 코드는 설계 예시이며, 실제 파일 추가와 문법 설명은 해당 단계에서 진행한다.

```ts
type YN = 'Y' | 'N'

type User = {
  id: string
  name: string
  email: string
  department: string
  activeYn: YN
}
```

ID는 등록 시 사용자가 직접 입력한다. 필수값이며 앞뒤 공백을 제거해 저장하고, 대소문자를 무시하여 중복을 검사하되 입력한 대소문자는 유지한다. 배열 순서나 사용자 이름에서 생성하지 않는다. 특정 사번 형식이나 로그인 연동 규칙을 기본 템플릿에 강제하지 않는다. 조직별 식별 체계와 통합 로그인 연동은 해당 프로젝트에서 별도로 구현한다. 활성 여부는 `activeYn`에 `Y`(활성) 또는 `N`(비활성)으로 저장하며, 표의 헤더는 `활성 여부`이고 값은 `Y`, `N` 그대로 표시한다. 부서 미입력은 빈 문자열로 저장하고 표에는 `-`로 표시한다. 실제 인물 정보 대신 가상 이름과 `example.com` 이메일을 사용한다.

| 상태 | 관리 위치 | 이유 |
| --- | --- | --- |
| 현재 화면 | URL | 직접 주소 입력·뒤로 가기와 화면을 맞춤 |
| Left 접기 여부 | `AppLayout` | Top과 Left가 함께 사용 |
| 검색 입력값 | 검색 Form | 입력과 적용 조건을 구분 |
| 적용 검색 조건·현재 페이지 | `UserPage` | 목록에 어떤 데이터를 보여 줄지 결정 |
| 조회 결과 `items`·`total`, 조회 중·조회 오류 | `UserPage` | 한 페이지 결과와 전체 건수, 피드백 연결 |
| 모달 열림·수정 대상·저장 중 | `UserPage` | 등록·수정과 목록 갱신 연결 |
| 등록·수정 입력값 | 입력 Form | 검증과 초기값 관리 |
| 원본 가상 데이터 | `userApi.ts`의 모듈 내부 | 페이지 이동 후에도 앱 실행 중 변경 유지 |

08–09에서는 원본 배열과 조건으로 필터링된 목록·총 건수를 계산하고 별도 state로 중복 저장하지 않는다. 10-A부터 그 계산은 조회 함수로 옮긴다. 비동기 조회 후에는 화면에 전체 원본 배열이 없으므로 `items`와 `total`을 하나의 조회 결과로 저장한다. `total`을 현재 페이지의 `items.length`로 대체하지 않는다. Form이 관리하는 입력값도 같은 용도의 `useState`로 다시 관리하지 않는다.

## 모의 API와 비동기 흐름

### 화면이 사용하는 데이터 계약

`userApi.ts`는 아래 기능 전용 함수를 제공한다. API는 호출 방법과 반환값의 약속이며, 1차 구현에는 실제 HTTP 요청이 없다. 타입과 함수는 각각 필요한 단계에서 추가한다. 1차는 브라우저 메모리의 데이터를 Promise로 반환하므로 Axios를 사용하지 않는다. 이후 실제 HTTP 요청은 Axios로 구현하고, 화면이 받는 기능별 반환 타입은 가능한 한 유지한다.

```ts
// 10-A에서 src/features/users/types.ts에 도입한 조회 계약.
type UserListQuery = {
  name: string
  activeYn: '' | YN // 빈 문자열은 전체
  page: number    // 1부터 시작
  pageSize: number
}

type UserListResult = {
  items: User[]   // 요청한 한 페이지
  total: number   // 검색 조건에 맞는 전체 건수
}
```

| 함수 | 입력 | 결과 | 도입 |
| --- | --- | --- | --- |
| `getUsers` | `UserListQuery` | `Promise<UserListResult>` | 10-B |
| `createUser` | 직접 입력한 ID를 포함한 `UserFormValues` | `Promise<User>` | 13-A |
| `updateUser` | ID, `UserFormValues` | `Promise<User>` | 14-B |
| `deleteUsers` | ID 배열 | `Promise<void>` | 15-B |

검색 조건의 앞뒤 공백·대소문자 규칙은 조회 함수에서 적용한다. `page`와 `pageSize`는 양의 정수이고 UI는 1차에 `pageSize=10`을 보낸다. 총 건수는 페이지를 자르기 전에 계산한다. 범위를 벗어난 페이지는 빈 `items`와 정확한 `total`을 반환하며, UI가 필요한 페이지 보정을 결정한다.

08–09의 로컬 검색·페이지 처리는 학습을 위한 중간 구현이다. 09에서는 별도 Ant Design `Pagination`에 제어된 `current`·`pageSize`·`total`을 연결하고, 잘라 낸 행을 AG Grid의 `rowData`에 전달한다. 그리드 자체 페이지 기능은 끈다. 10-A에서는 계산을 `queryUsers`라는 동기 함수로 옮겨 계약부터 익히고, 10-B에서 그 함수를 사용하는 비동기 `getUsers`를 연결한다. 이후 페이지와 그리드는 전달받은 `items`를 다시 필터링하거나 `slice`하지 않는다. 2·3페이지에서 이중으로 페이지를 잘라 빈 그리드가 되지 않는지 확인한다. Enterprise의 Server-Side Row Model은 사용하지 않는다. [Ant Design Pagination 안내](https://ant.design/components/pagination/)

모의 API는 짧은 지연을 두고 결과를 반환한다. 원본 배열은 API 모듈 내부에서 관리하며, 반환 배열과 각 사용자 객체를 분리해 UI의 수정이 원본 데이터에 전파되지 않게 한다. 등록·수정은 API에서도 필수값·이메일·Y/N을 검증한다. 중복 이메일이나 이미 없는 ID의 수정·삭제는 실패로 처리한다. 이 검증은 서버의 데이터 경계를 연습하는 모의 구현이다.

### 요청과 결과의 흐름

```text
사용자 동작 → 페이지의 이벤트 처리 → 모의 API 호출
           → 진행 표시 → 성공 후 목록 갱신 / 실패 안내
```

화면 진입과 적용 조건·페이지 변경에 따른 조회는 하나의 `useEffect` 경로로 처리한다. 검색·초기화 이벤트에서는 조건과 `page=1`을 함께 갱신하고, 저장 성공·재시도는 같은 조회 경로를 다시 실행하게 한다. 이벤트와 Effect에서 같은 조회를 각각 호출하지 않는다. 등록·수정·삭제 요청 자체는 사용자 이벤트에서만 보낸다.

화면 이동이나 연속 검색·페이지 변경 후 늦게 도착한 이전 결과가 최신 화면을 덮지 않도록 Effect 정리에서 이전 요청 결과를 무시한다. 이전 요청의 오류나 로딩 종료도 최신 상태를 바꾸지 않아야 한다. 이 처리는 비동기 도입 단계부터 포함한다. 개발 환경의 `StrictMode`를 끄지 않고 추가 실행에도 동작이 맞는지 확인한다. [React Effect 공식 문서](https://react.dev/learn/synchronizing-with-effects)

조회·저장·삭제 실패는 명시적인 개발용 모의 실패 설정으로 재현한다. 평상시에는 정상 동작하며 무작위 실패는 넣지 않는다. 실패 설정·해제 위치, 재현 순서, 기대 결과, 실제 확인 결과를 해당 학습 단계에 기록한다. 저장 실패와 저장 성공 후 재조회 실패는 따로 재현할 수 있게 한다. 정해진 지연으로 이전 조회가 나중에 끝나는 경우도 확인한다. 실패 주입 방식은 해당 단계에서 최소한으로 구현하고 기본 업무 화면에 개발용 설정을 섞지 않는다.

빈 결과와 조회 실패는 서로 다른 안내를 보여 준다. 조회 중에는 대기 표시와 함께 이전 결과의 행 작업을 막고, 조회 실패 시 이전 결과를 최신 결과처럼 제시하지 않는다. 실패 시 재시도는 조회만 다시 수행한다. 저장·삭제는 성공했으나 이후 목록 재조회가 실패한 경우에도, 성공한 변경 요청을 다시 보내지 않고 목록 조회를 재시도한다.

조회 실패 후에는 별도 재시도 버튼 없이 검색 버튼이나 Enter로 다시 조회한다. 검색 폼의 현재 입력값을 적용하고 1페이지부터 조회하는 기존 검색 동작을 사용한다. 조회 중에는 오류 안내·이전 목록·총 건수·페이지 버튼을 숨기고, 다시 실패하면 오류 안내를 표시한다. 이후 저장·삭제 성공 후 조회 실패도 검색으로 목록만 다시 조회하며 성공한 변경 요청을 반복하지 않는다.

**데이터 보존 범위는 앱을 연 뒤 새로고침하기 전까지**다. 메뉴 이동 시에는 변경이 유지되지만, 브라우저 새로고침 시 가상 초기 데이터로 돌아간다. 다른 탭과 데이터를 공유하지 않는다. 검색·페이지·모달 상태는 화면 재진입 시 초기화한다. 이 제한을 화면 설명과 README에 표시한다. localStorage나 DB는 1차에 추가하지 않는다.

### 실제 서버로 전환할 때

실제 HTTP 호출 도구는 **Axios**로 정한다. 페이지·표·입력 컴포넌트는 기능별 API 함수를 호출하며, 그 함수 내부에서 Axios 요청과 서버 응답 변환을 처리한다. 서버 응답 본문인 `response.data`를 화면용 타입으로 맞춰 반환하고, 컴포넌트에 `AxiosResponse` 전체를 전달하지 않는다. 검색 매개변수·페이지 번호·총 건수가 서버와 다르면 이 경계에서 맞춘다. [Axios 시작 안내](https://axios-http.com/docs/intro)

HTTP 연결 시에는 설치와 사용자 목록 조회 하나부터 진행한다. 필요한 기본 주소·대기 시간 설정은 Axios 인스턴스에 모으고, 서버 오류·응답 없는 요청·취소 등을 구분해 기존 화면의 오류 처리로 연결한다. 인증, 인터셉터(요청·응답 전후의 공통 처리), 자동 재시도는 실제 요구가 생긴 단계에서 도입한다. [Axios 인스턴스](https://axios-http.com/docs/instance), [오류 처리](https://axios-http.com/docs/handling_errors)

실제 주소, 인증·권한, 서버 검증과 CORS는 서버 계약이 생겼을 때 별도로 구현·검증한다. Axios를 선택해도 TypeScript 타입만으로 서버 응답이 실행 중 검증되는 것은 아니다. 미사용 Axios 파일, 빈 HTTP 클라이언트, 전환용 환경변수는 지금 추가하지 않는다.

### 사용자 그룹 관리와 권한 확장 후보

사용자 관리의 조회·등록·수정·삭제를 완성한 뒤, 두 번째 업무 화면 후보로 **사용자 그룹 관리**를 검토한다. 로드맵의 기존 후보는 공통 코드 조회이며, 사용자 그룹 관리로의 교체는 아직 확정하지 않는다. 현재 학습 순서와 1차 범위는 유지하고, 권한용 코드·설정·의존성을 미리 추가하지 않는다.

확장은 다음 순서로 작은 작업을 나누며, 실제 구현 순서는 해당 단계에서 정한다.

1. 사용자 그룹 목록·등록·수정을 만든다.
2. 사용자와 그룹의 소속 관계를 관리한다.
3. 그룹에 메뉴별 기능 권한을 설정한다.
4. 모의 사용자를 전환하며 메뉴 접근과 기능 사용 제한을 확인한다.
5. 실제 백엔드 연결 시 인증된 사용자와 서버의 API 권한 검사를 연결한다.

권한의 기본 관계는 **사용자 → 사용자 그룹 → 메뉴별 기능 권한**이다. 그룹은 관리자·조회 담당자·운영 담당자 같은 권한 묶음이며 부서 등 조직 분류와 구분한다. 그룹 선택 후 소속 사용자와 메뉴별 권한을 관리하는 화면을 후보로 둔다.

권한은 개별 버튼 식별자가 아니라 업무 동작을 기준으로 정의한다. 같은 업무를 수행하는 여러 버튼은 동일한 권한을 확인한다. 사용자 관리라면 조회·등록·수정·삭제를 기준으로 하고, 승인·일괄 처리 등 별도 실행 권한은 해당 메뉴에 실제 기능이 생겼을 때 추가한다. 등록·수정을 함께 허용해도 되는 업무는 쓰기 권한으로 묶을 수 있으며, 모든 메뉴에 동일한 권한 항목을 강제하지 않는다.

초기 적용 규칙의 후보는 다음과 같다. 구현 전에 실제 사용자 동작에 맞춰 확정한다.

- 조회 권한을 메뉴 접근 기준으로 사용하고, 메뉴 표시와 URL 직접 접근에 같은 기준을 적용한다.
- 등록·수정·삭제는 조회 권한과 함께 부여하도록 한다.
- 부여되지 않은 권한은 기본적으로 허용하지 않는다.
- 여러 그룹 소속을 허용한다면 소속 그룹의 허용 권한을 합친다. 명시적 거부와 사용자 개인별 예외 권한은 초기 범위에 넣지 않는다.
- 권한 설정 화면은 행에 메뉴, 열에 해당 메뉴의 기능 권한을 배치하는 체크박스 표를 후보로 둔다.

백엔드 없는 모의 사용자 전환은 권한에 따른 화면 동작을 시연하기 위한 것이다. 실제 인증이나 보안을 제공하는 기능으로 표현하지 않는다. 메뉴·버튼 제어와 별도로 실제 서버는 각 API에서 인증된 사용자의 권한을 검사해야 한다. 그룹 관리 화면의 완성과 권한 적용의 완성은 구분한다.
