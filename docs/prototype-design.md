# 1차 프로토타입 설계

## 목표와 문서 사용법

다양한 SI 프로젝트에서 출발점으로 사용할 수 있는 React + TypeScript 프런트엔드를 만든다. 1차 목표는 공통 화면 틀과 사용자 관리 한 화면을 끝까지 동작시키는 것이다. 사용자 관리는 목록·검색·입력·검증·저장 흐름을 익히기 위한 대표 기능이며, 다른 프로젝트의 업무 화면으로 교체할 수 있게 공통 틀과 분리한다.

이 문서는 **1차 완료 시점의 설계**다. 현재 구현된 기능 목록이나 미리 생성할 파일 목록이 아니다. 구현 순서와 진행 상태는 [단계별 개발·학습 계획](./learning-plan.md)을 따른다. 필요한 파일과 설정은 해당 단계에서 추가한다.

## 1차 범위

| 영역 | 1차에 완성할 내용 |
| --- | --- |
| 공통 화면 틀 | Top / Left / Content 분리, Left 접기·펼치기 |
| 화면 이동 | 홈과 사용자 관리 이동, URL에 따른 메뉴 선택, 없는 주소 안내 |
| 사용자 목록 | 이름·이메일·부서·상태 표시, 페이지 이동 |
| 검색 | 이름 부분 검색, 활성·비활성 조건, 검색·초기화 |
| 등록·수정 | 모달 입력, 필수값·이메일 형식 검증, 저장 |
| 삭제 | 대상 이름을 보여 주는 확인, 취소·삭제 |
| 비동기 처리 | 모의 데이터 조회·저장, 로딩·빈 결과·오류·재시도 |
| 공통 표현 | 화면 제목, 작업 성공·실패 안내, 한국어 UI |
| 마무리 | 코드 검사, 빌드, 브라우저 동작 확인, 실행·확인 방법 문서화 |

실제 서버·DB, 로그인·권한, 파일 첨부·엑셀, 다중 탭, 통계 대시보드, 모바일 전용 화면은 이후 범위다. 전역 상태 라이브러리, 데이터 캐시 라이브러리, 범용 CRUD 생성기도 1차에 추가하지 않는다. 현재 기능에서 필요성이 생기면 다음 설계에서 판단한다.

## Top / Left / Content 구조

Top은 화면 전체 너비를 사용하고, 그 아래에 Left와 Content를 좌우로 배치한다.

```text
┌──────────────────────────────────────────────────────────┐
│ Top: 프로젝트 이름 / Left 접기·펼치기 버튼               │
├──────────────┬───────────────────────────────────────────┤
│ Left         │ Content                                   │
│              │                                           │
│ · 홈         │ 화면 제목과 설명                          │
│ · 사용자 관리│ 검색 조건                                 │
│              │ 조회 건수 / 등록 버튼                     │
│              │ 목록 표 / 페이지 이동                     │
│              │                                           │
└──────────────┴───────────────────────────────────────────┘
```

| 영역 | 역할 | 구현 방향 |
| --- | --- | --- |
| Top | 프로젝트 식별과 공통 조작 | `Layout.Header`, 프로젝트 이름, 접기 버튼 |
| Left | 업무 화면 이동과 현재 위치 표시 | `Layout.Sider`, `Menu` |
| Content | 선택한 화면의 내용 | `Layout.Content`, 라우트에 맞는 페이지 |

Ant Design은 `Layout` 아래에 `Header`, `Sider`, `Content`와 내부 `Layout`을 조합할 수 있다. 이 구성을 사용한다. [Ant Design Layout 공식 문서](https://ant.design/components/layout/)

초기 기준은 Top 높이 64px, Left 너비 208px, 접은 너비 80px, Content 안쪽 여백 24px이다. 업무용 데스크톱 화면을 대상으로 하며, 1280×720과 1024×768에서 확인한다. 표가 넓으면 표 내부에서 가로 스크롤하고, 내용이 길면 Content가 세로 스크롤한다. Top과 Left는 화면에 유지한다. CSS는 이 배치와 읽기 쉬운 간격에 필요한 것만 작성한다.

접기 상태는 `AppLayout`이 관리하고 Top의 버튼과 Left에 전달한다. 화면을 이동해도 공통 틀은 유지한다. 인증 기능이 없으므로 Top에 로그인 사용자나 로그아웃 버튼은 넣지 않는다.

## 화면과 사용자 동작

### 홈 `/`

프로젝트의 용도와 사용자 관리 화면으로 이동하는 링크를 보여 준다. 첫 진입 시 무엇을 할 수 있는지 알려 주는 작은 시작 화면이다. 통계나 차트는 추가하지 않는다.

### 사용자 관리 `/users`

사용자는 검색 조건을 입력하고 **검색**을 눌러 목록을 좁힌다. 검색 조건은 이름과 상태이며, 상태에는 전체·활성·비활성이 있다. 이름은 앞뒤 공백을 제거하고 부분 일치로 검색한다. 영문 대소문자는 구분하지 않는다.

입력 중인 조건과 실제 적용된 조건을 구분한다. 입력만으로 표가 바뀌지 않으며, Enter로도 검색할 수 있다. **초기화**는 입력값과 적용 조건을 모두 기본값으로 돌린다. 새 검색과 초기화는 1페이지로 이동한다.

표는 한 페이지에 10건을 표시한다. 모의 데이터는 25건 이상 준비해 페이지 이동을 실제로 확인한다. 열은 이름·이메일·부서·상태·작업으로 구성하고, 작업 열은 수정·삭제 단계에서 추가한다. 항목을 식별하는 `rowKey`는 사용자 ID를 사용한다.

**등록**은 빈 입력 모달을 연다. **수정**은 선택한 사용자의 값을 같은 입력 모달에 채운다. 이름·이메일·상태는 필수이고 부서는 선택 입력이다. 상태 기본값은 활성이다. 비어 있는 이름과 잘못된 이메일은 입력 단계에서 안내한다. 중복 이메일은 모의 API에서 검사하며, 수정 시 자기 자신의 이메일은 중복으로 취급하지 않는다.

저장 중에는 중복 제출을 막고 진행 상태를 표시한다. 저장 실패 시 입력값을 유지한다. 저장 성공 시 모달을 닫고 목록을 다시 조회한다. 등록·수정 후에는 검색 조건을 유지하면서 1페이지로 이동한다. 조건에 맞지 않는 사용자는 목록에 보이지 않을 수 있다.

**삭제**는 대상 이름과 함께 확인한다. 취소하면 데이터가 바뀌지 않는다. 삭제 후 목록을 다시 조회하고, 마지막 페이지가 사라졌으면 유효한 페이지로 이동한다.

### 없는 주소 `*`

Top / Left / Content 틀 안에서 없는 화면이라는 안내와 홈 이동 링크를 보여 준다. 홈이나 사용자 관리 메뉴가 잘못 선택된 상태로 표시되지 않게 한다.

URL과 화면 연결에는 React Router의 Declarative 모드를 사용한다. 기본 화면 전환에 필요한 `BrowserRouter`, `Routes`, `Route`, `Outlet`, `Link`, `useLocation`부터 해당 단계에서 익힌다. [React Router 모드 설명](https://reactrouter.com/start/modes), [라우팅 공식 문서](https://reactrouter.com/start/declarative/routing)

## 기술 선택

| 기술 | 역할 | 도입 시점 |
| --- | --- | --- |
| React + TypeScript | 컴포넌트, 상태, 데이터·함수 타입 | 기존 구성 사용 |
| Vite + ESLint | 개발 서버, 빌드, 코드 검사 | 기존 구성 사용 |
| Ant Design | Layout, Menu, Table, Form, Modal 등 | 이미 설치됨. 필요한 컴포넌트만 단계별 사용 |
| React Router | URL에 따른 화면 이동 | 화면 전환 단계에서 설치 |
| CSS | 화면 틀 크기·간격·스크롤 | 배치 단계부터 필요한 만큼 작성 |
| 비동기 모의 API | 서버 없이 조회·저장과 대기·실패 흐름 연습 | 비동기 조회 단계에서 작성 |

현재 설치된 버전을 기준으로 개발하고, 설계 때문에 기존 의존성을 업그레이드하지 않는다. React Router 설치 시에는 현재 프로젝트와 호환되는 버전과 공식 설치 방법을 다시 확인한다. Declarative 모드의 공식 설치 패키지는 `react-router`다. [React Router 설치 공식 문서](https://reactrouter.com/start/declarative/installation)

사용자 데이터 타입을 정의하는 단계에서 앱의 TypeScript `strict` 검사를 켠다. `strict`는 더 엄격한 타입 검사를 활성화하는 설정이다. 발생하는 오류는 타입과 값의 관계를 이해하며 해결한다. [TypeScript strict 공식 문서](https://www.typescriptlang.org/tsconfig/strict.html)

## 코드 구조

아래는 1차 완료 시점의 예상 구조다. 빈 폴더나 미래 단계의 파일을 먼저 만들지 않는다. 파일명은 구현 중 더 적절한 이름으로 조정할 수 있다.

```text
src/
  main.tsx                     # React 시작점, 필요한 Provider
  App.tsx                      # 라우트와 레이아웃 연결
  styles.css                   # 최소한의 전역 배치 스타일
  layout/
    AppLayout.tsx              # 공통 화면 틀, Left 접기 상태
    TopBar.tsx                 # Top 표시와 접기 버튼
    SideMenu.tsx               # 메뉴 표시, URL에 따른 선택
  components/
    PageHeader.tsx             # 홈·사용자 화면에서 공유하는 제목
  pages/
    HomePage.tsx
    NotFoundPage.tsx
  features/
    users/
      UserPage.tsx             # 조회 조건·목록·모달·저장 흐름 연결
      types.ts                 # 사용자, 검색 조건, 입력값 타입
      mockUsers.ts             # 초기 가상 데이터
      api/
        userApi.ts             # 모의 조회·등록·수정·삭제
      components/
        UserTable.tsx          # 표 표시, 행 작업 이벤트 전달
        UserSearchForm.tsx     # 조건 입력, 검색·초기화 이벤트 전달
        UserFormModal.tsx      # 등록·수정 입력과 검증
docs/
  prototype-design.md
  learning-plan.md
```

공통 틀은 사용자 데이터와 검색 규칙을 알지 않는다. 사용자 관리 관련 파일은 `features/users`에 모으고, 조회·저장 구현은 UI에서 분리한다. 이 경계를 유지하면 다른 업무 화면을 같은 틀에 추가하거나 사용자 예제를 교체하기 쉽다.

`PageHeader`는 홈과 사용자 관리의 제목 표현을 실제로 공유할 때 만든다. 범용 검색 폼이나 범용 테이블은 만들지 않는다. 표·검색·입력 모달은 사용자 기능의 컴포넌트로 유지한다.

## 데이터와 상태

사용자 데이터의 기본 모양은 다음과 같다. 이 코드는 설계 예시이며, 실제 파일 추가와 문법 설명은 해당 단계에서 진행한다.

```ts
type UserStatus = 'active' | 'inactive'

type User = {
  id: string
  name: string
  email: string
  department: string
  status: UserStatus
}
```

ID는 모의 API가 생성하며, 배열 순서나 사용자 이름을 ID로 사용하지 않는다. 부서 미입력은 빈 문자열로 저장하고 표에는 `-`로 표시한다. 실제 인물 정보 대신 가상 이름과 `example.com` 이메일을 사용한다.

| 상태 | 관리 위치 | 이유 |
| --- | --- | --- |
| 현재 화면 | URL | 직접 주소 입력·뒤로 가기와 화면을 맞춤 |
| Left 접기 여부 | `AppLayout` | Top과 Left가 함께 사용 |
| 검색 입력값 | 검색 Form | 입력과 적용 조건을 구분 |
| 적용 검색 조건·현재 페이지 | `UserPage` | 목록에 어떤 데이터를 보여 줄지 결정 |
| 조회한 목록·조회 중·조회 오류 | `UserPage` | 조회 결과와 피드백 연결 |
| 모달 열림·수정 대상·저장 중 | `UserPage` | 등록·수정과 목록 갱신 연결 |
| 등록·수정 입력값 | 입력 Form | 검증과 초기값 관리 |
| 원본 가상 데이터 | `userApi.ts`의 모듈 내부 | 페이지 이동 후에도 앱 실행 중 변경 유지 |

필터링된 목록과 총 건수는 원본 목록과 조건에서 계산한다. 같은 결과를 별도 state로 중복 저장하지 않는다. Form이 관리하는 입력값도 같은 용도의 `useState`로 다시 관리하지 않는다.

## 모의 API와 비동기 흐름

`userApi.ts`는 조회·등록·수정·삭제 함수를 제공한다. 반환 타입은 각각 `Promise<User[]>`, `Promise<User>`, `Promise<User>`, `Promise<void>`로 시작한다. 등록·수정 입력값 타입에는 ID를 포함하지 않는다. 이 타입은 저장 단계에서 추가한다.

모의 API는 짧은 지연을 두고 결과를 반환하며 실제 HTTP 요청을 보내지 않는다. 원본 배열을 UI가 직접 수정할 수 없도록 반환값을 분리한다. 검색과 페이지 나누기는 조회한 목록을 기준으로 프런트엔드에서 처리한다.

```text
사용자 동작 → 페이지의 이벤트 처리 → 모의 API 호출
           → 진행 표시 → 성공 후 목록 갱신 / 실패 안내
```

화면 진입 시 조회는 `useEffect`에서 시작하고, 검색 조건 적용과 등록·수정·삭제는 사용자 이벤트에서 처리한다. 화면 이동 후 도착한 이전 조회 결과가 현재 화면에 반영되지 않도록 정리 처리를 한다. 개발 환경의 `StrictMode`에서 Effect가 추가 실행되는 경우도 확인한다. [React Effect 공식 문서](https://react.dev/learn/synchronizing-with-effects)

조회·저장·삭제 실패는 명시적인 개발용 모의 실패 설정으로 재현한다. 평상시에는 정상 동작하며 무작위 실패는 넣지 않는다. 조회 실패 설정과 재시도 확인 방법은 오류 처리 단계에서 기록하고, 저장·삭제 실패 재현 방법은 각 기능을 연결하는 단계에서 추가한다.

빈 결과와 조회 실패는 서로 다른 안내를 보여 준다. 실패 시 재시도는 조회만 다시 수행한다. 저장은 성공했으나 이후 목록 재조회가 실패한 경우에도, 성공한 저장을 다시 보내지 않고 목록 조회를 재시도한다.

**데이터 보존 범위는 앱을 연 뒤 새로고침하기 전까지**다. 메뉴 이동 시에는 변경이 유지되지만, 브라우저 새로고침 시 가상 초기 데이터로 돌아간다. 검색·페이지·모달 상태는 화면 재진입 시 초기화한다. 이 제한을 화면 설명과 README에 표시한다. 실제 API로 바꿀 때는 데이터 계약과 서버 측 검색·페이지 처리도 다시 설계한다.

## 1차 완료 기준

- Top / Left / Content가 분리되고 접기·펼치기와 Content 스크롤이 동작한다.
- 홈·사용자 관리 이동, 직접 주소 진입, 뒤로·앞으로 가기, 없는 주소 안내가 동작한다.
- 이름·상태 검색과 초기화, 빈 결과 안내, 페이지 이동이 동작한다.
- 등록·수정 검증, 저장 중 중복 제출 방지, 성공·실패 안내가 동작한다.
- 삭제 확인·취소·삭제와 삭제 후 페이지 보정이 동작한다.
- 모달을 다시 열었을 때 이전 입력값이나 검증 오류가 잘못 남지 않는다.
- 조회 중·실패·재시도를 확인하고, 데이터 보존 범위를 설명할 수 있다.
- 공통 틀·업무 화면·조회 및 저장 구현의 역할을 구분할 수 있다.
- TypeScript 검사·ESLint·빌드가 통과하고, 별도로 브라우저 동작을 확인한다.
- README에 실행 방법, 범위·제한, 새 업무 화면 추가 위치, 수동 확인 절차를 기록한다.

정적 호스팅에서 `/users` 같은 주소로 직접 진입하려면 서버가 앱의 `index.html`을 반환하도록 구성해야 한다. 실제 배포는 1차 범위에 포함하지 않으며, 배포 단계에서는 해당 환경의 설정과 직접 진입을 따로 검증한다. [React Router SPA 배포 안내](https://reactrouter.com/how-to/spa)

## 1차 이후의 판단

실제 서버 계약이 정해지면 HTTP 통신을 연결하고, 인증 요구가 정해지면 로그인·권한을 설계한다. 여러 화면에서 같은 처리의 반복이 확인되면 공통화나 상태 관리 도구를 검토한다. 1차 완료만으로 실무 숙련을 가정하지 않고, 새 업무 화면 적용과 실제 API·테스트 경험을 이어 간다.
